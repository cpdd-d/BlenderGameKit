## 1. 结论

> 当前状态以 §8（两处小修补丁后的 3 次复测）为准；§2~§7 保留补丁前的原始测量。

- **L1 通过 2 项、不通过 1 项**：`world_load_s` 3.35s、`rss_mb` 848MB 达标；`chunk_build_ms` p99 ≈ 9ms，未达 4ms。

- **L3 大幅改善**：draw calls 464（基线 1736），三角面 0.85M（基线 3.73M）。
- 不达标项与渲染距离无关，**不建议现在降 16→12**；先修分段预算与 0.25s 全场景扫描，详见 §5。
- **补丁后（§8）**：静止 >33ms 帧归零、L2 全部达标；`chunk_build_ms` p99 8.15~9.47ms，仍未达 4ms —— 单段首建本身 8~15ms，与"一帧挤几段"无关。16→12 回退建议见 §8.4，判断仍为不建议执行。

## 4. 不达标项归因

1. **`chunk_build_ms` p99 ≈9ms**：`SECTION_PER_FRAME=2`，每段 3–5ms（首建 8–11ms），两段叠在一帧；`BUILD_BUDGET_US=3000` 只兜列与远景，不兜分段合成。
2. **静止 p99 34.7ms（5/180 帧）**：`_cull_placed` 每 0.25s 全场景扫描；180 帧窗口正好 5 次扫描，每帧比基线高约 28ms。物理体从 6400 降到 2304 后，同样口径 p99 降到 32ms / >33ms 帧为 0。
3. **走动 p99 18.6ms**：跨区块时近景列 + 分段合成落在同一帧，叠加基础 6.4ms 后越过 16.7ms；max 43ms 对应一次扫描/整段首建。
4. **进世界最大帧 78.6ms**：加载屏内出生点扫描 + 首段合成，不发生在放开操作后。

## 5. 回退建议与判断

**建议：现在不降 16→12，也不降 8。**

理由：

- L1 的 `chunk_build_ms` 由“近景分段每帧建几段”决定，与渲染距离无关；降到 12/8 后跨区块仍要建同样多的近景段，p99 不会改善。
- L2 的静止 p99 由 0.25s 全场景扫描 + 出生点 5×5 碰撞决定；5×5 是固定门槛，降档也不会减少这圈物理体。
- L3 本来就远低于门槛（464 vs 3500），降档只会让画质变差、收益接近于零。

**优先修两处机制（建议作为 M2a 补丁，不并进 M2b 地形重定）：**

1. 给分段合成加时间预算（或 `SECTION_PER_FRAME=1` + 剩余预算），把单帧 build 压到 ≤4ms。
2. `_cull_placed` 改为登记表增量巡检，去掉每 0.25s `find_children` 全场景扫描；或进入世界后立即把出生点 5×5 碰撞收敛到玩家 ±1 区块。

修复后连续 3 次测量仍不达标，再按 16→12→8 回退；每次回退记录指标与原因并交用户确认。

## 8. 补丁复测（两处小修后，连跑 3 次）

### 8.1 改动内容

1. **分段构建吃时间预算**：删掉 `SECTION_PER_FRAME=2` / `SECTION_PER_FRAME_MENU=4`；`_step_build()` 与 `spawn_build_step()` 改为每建一段再判 `BUILD_BUDGET_US`（加载期 `BUILD_BUDGET_MENU_US`），并把分段循环放在列 / 远景之后，用 `did_terrain` 标记"这一帧铺过列或远景"——铺过就不再合分段，两类重活不叠帧。
2. **`_cull_placed` 增量巡检**：`_ready()` 接 `SceneTree.node_added`，新增节点时用 `_adopt_placed_node()` 登记（`StaticBody3D`、名字不以 `地形_` 开头、能认出方块类型才收）；`_cull_placed` 只遍历 `_placed_nodes`，首次调用仍做一次兜底扫描（覆盖"信号连接前已在场景里"的方块），之后不再 `find_children` 全场扫描。

### 8.4 16→12 回退建议（按约定给出，不自行执行）

**是否降 16→12：建议不降。**

- 剩余唯一不达标项是 `chunk_build_ms` p99 8.15~9.47ms。走动采样里，这一帧的构建量**已经只有一段**（`did_terrain` 保证不与列 / 远景叠帧），p99 就是单段首建本身的耗时（§8.2 单段 p99 11.9~13.3ms、max 15.1ms）。
- 近景固定是玩家所在区块 ±1（3×3 个区块、每区块 4 段），**与渲染距离档位无关**；降到 12 或 8，跨区块时仍要建同样多的段，p99 不变，只会损失视距。
- L2 三项在补丁后已全部达标（窗口口径 p99 ≤11.91ms、max ≤30.2ms、>33ms 帧为 0），L1 的 `world_load_s` / `rss_mb` 也达标，降档没有收益。

真正要继续压 `chunk_build_ms` 的方向（本轮未动，超出"两处小修"范围）：把**单段合成**本身拆到多帧（按 x 列条带增量填 SurfaceTool + 最后 commit），或把 `_height_at` / `_open_mask` 的重复计算缓存到区块级；这属于 M2b 之外的独立补丁，建议单独起一项。

### 8.5 复测结论

- 静止 >33ms 帧：**3/3 次归零**（补丁前窗口 5/180、无头 12/180）。
- `chunk_build_ms` p99 ≤4ms：**3/3 次未达标**（8.15 / 8.66 / 9.47ms），不满足"p99 ≤4ms 且静止无 33ms 以上帧"的合并条件。
- 其它都正常：`MINECRAFT_CHECK=OK`、`MINECRAFT=OK`，放置 / 剔除 / 挖掘分段重建 / 迟滞 / 迁移等既有断言全绿；draw calls 464、三角面 845,622 与补丁前一致。
- 按用户约定：**停在这里，等用户决定**是否接受 8~9.5ms 的 `chunk_build_ms` p99（改为把单段合成拆分列入后续），或执行 16→12 回退（本报告判断收益为零）。
