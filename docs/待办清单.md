## 一、正在做 / 用户已点名

### 1.1 节点系统重构 ← **下一步就是它**

用户原话:"这效果确实可以了……你查询没有错误,那就进行节点系统吧"

目标 = **UPBGE 的自动识别 + 虚幻蓝图的动态引脚** 两者结合。

#### 从 UPBGE 学什么(看了用户截图里的 `Play Animation` 节点)

| UPBGE 有 | 我们现在 | 要加吗 |
|---|---|---|
| **`Started` / `Running` / `On Finish` 三个事件输出** | 没有事件输出 | **要**。做完动画接不了后续逻辑是硬伤 |
| **选物体后自动列出它身上的动作** | 手填动画名 | **要**。填错只能靠运行时警告 |
| `起始` / `结束` 帧 | 无 | 要 |
| `层` | 无 | 要(上下半身分离动画) |
| `速率`(负值倒放) | 有(速度) | 已有 |
| `Blend-In`(过渡秒数) | 无 | **要** |
| `混合模式` | 无 | 要 |
| 「属性修改」直接在节点上改 | 要跑去别的面板 | 要 |

#### 从虚幻蓝图学什么

- **动态引脚**:`Sequence` 节点能加任意多个执行输出;
  `Switch` 能加任意多个分支;`Make/Break Struct` 按结构定义长引脚。
- **通配/自动类型**:引脚类型跟着连线走。
- **节点内联注释**(蓝图里叫 Comment Box)。

#### UPBGE 那套的缺陷(用户自己指出的,要避开)

- 一次只能播一个动画,没有状态机
- 引脚数固定,不能自定义
- 「属性修改」塞在同一个节点里,节点越用越大

#### 建议的落地顺序

1. **先做动态引脚**(`Sequence` 可加任意分支、`Switch` 可加任意 case)
   —— 这是"蓝图感"的地基,后面所有节点都受益
2. **再做动画事件输出**(`Started` / `Running` / `On Finish`)
3. **然后物体属性变更自动刷新动画下拉列表**(选 Cube 就列出 Cube 的动作)
4. **最后做动画状态机节点**(状态表 + 转移条件,取代手拼分支网)

## 二、MMD / 骨骼动画相关的遗留

### 2.1 形态键动画 —— **已确认是好的,不是 bug**

实测(`.audit/mmd_render`,播放 `形态键动作`):

```
帧20 pos=0.119  形态键前5=["0.000","0.000","0.000","0.407","0.000"]
帧40 pos=0.255  形态键前5=["0.000","0.000","0.000","0.998","0.000"]
帧60 pos=0.388  形态键前5=["0.000","0.000","0.000","0.656","0.000"]
```

第 4 个形态键在 0 → 1.0 → 0 之间动。**导出、导入、驱动全链路正常。**

用户觉得"没生效"的原因:节点里动画名填的还是默认的 `idle`,
而模型里的动作叫 `形态键动作` / `骨骼动作`。改名字即可。
(运行时已经会打出可用动画名,见 2.2)

### 2.2 动画名下拉自动填充 ✅ 部分做了

现在填错会提示可用名字:

```
[GK] 动画不存在: idle。这个模型里可用的动画有: ["形态键动作", "骨骼动作"]
```

**还没做**:在 Blender 里就把下拉列表填好(见 1.1 第 3 步)。

### 2.3 骨架应该是网格的父级

Blender 的 glTF 导出器警告:

```
WARNING: Armature must be the parent of skinned mesh
```

用户的 `胡桃-海灯节_mesh` 和 `胡桃-海灯节_arm` 是**兄弟**。
我们已经专门支持了这种情况(顺着 `Armature` 修改器找回骨架),能用。
但官方推荐网格挂在骨架下面,更稳。

**要不要做**:导出时如果检测到这个结构,给一条提示告诉用户
"建议把网格拖到骨架下面"。**低优先级。**

## 三、渲染 / 卡通着色

### 3.1 `light()` 里的色阶可能没生效 ← **重要,没查透**

实测:`toon_exposure` 和 `shadow_tint` 改了以后,
渲染出来的 PNG **字节完全相同**(sha256 一致)。

说明 `light()` 里的卡通色阶那一段在当前 Godot 4.7 下
**基本没参与最终着色**(至少对那个 33 材质槽的 MMD 模型是这样)。
真正决定观感的是 `ALBEDO` + `EMISSION` 加法项。

**这意味着**:现在角色的"卡通感"其实主要来自**贴图本身**,
而不是我们的色阶。想要真正的 cel shading,这一段必须查通。

**排查方向**:
- Godot 4.7 里 `light()` 是否需要 `render_mode` 配合?
- `DIFFUSE_LIGHT` 是否被引擎的 tonemap/ambient 路径吃掉了?
- 换个简单模型(一个球 + 一盏灯)做最小复现

### 3.2 描边(outline)没接进导出流程

`shaders/gk_outline.gdshader` 写好了,但 `TOON_MATERIAL_TEMPLATE`
里没有 `next_pass`,导出的材质**不会描边**。
二次元角色没有描边会少很多味道。

### 3.3 面部 SDF 阴影没启用

`gk_toon.gdshader` 里有完整的 `face_sdf` 实现(能画出动漫那种
"一条干净阴影线"而不是脏兮兮的明暗交界),但
`TOON_MATERIAL_TEMPLATE` 里 `face_sdf_mix = 0`。

需要:导出时给面部的材质单独开 `face_sdf_mix`,并生成/导出 SDF 贴图。
Blender 侧还有 `GK_OT_SyncFaceAngle` 算子可以复用。

## 四、性能

### 4.1 导出慢 —— 瓶颈确认在 glTF 导出器,不在我们

用户 49 MB / 1056 骨骼的工程,实测各步骤:

| 步骤 | 耗时 |
|---|---|
| create_project | 0.05s |
| export_tree(脚本) | 0.00s |
| 检查无材质 | 0.00s |
| collect_physics | 0.00s(2301 个碰撞体) |
| write_materials | 0.02s(32 个材质) |
| export_textures | 0.49s(3 张贴图) |
| copy_shaders | 0.02s |
| **export_scene_glb** | **14.19s** |
| **export_subtree_glb(角色)** | **~12s** |
| **合计** | **~26s** |

用户日志里的三次导出:14.4s + 16.5s + 27.6s。

**结论**:我们自己的部分(材质+贴图+shader)加起来 **0.5 秒**,
其余全是 Blender 的 glTF 导出器在处理
25k 顶点 × 1056 骨骼 × 63 形态键。

**"只导出改动过的部分"收益有限** —— 模型改了就必须重导 glb,
省下来的是那 0.5 秒,不是 26 秒。

**可能有效的方向**(都没试):
- 导出 glb 时关掉不需要的东西(`export_tangents=False` 之类)
- 用 Draco 压缩(日志里提示 Draco 可用)
- 导出后台跑 + 进度条,至少让用户知道在动

### 4.2 导出时没有进度反馈

26 秒里界面是卡住的,用户会以为死了。**低优先级但体验差**。
