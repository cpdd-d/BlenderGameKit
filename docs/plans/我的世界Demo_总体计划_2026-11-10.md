> 状态：待评审（本文件只做计划与拆解，不含任何源码改动）
> 线划分：L1 示例线（T*，只改 demo 生成器/检查脚本与生成产物）；L2 本体线（C*，只改 BlenderGameKit 本体与 tests）
> 适用工程：`examples/demo_minecraft/我的世界_godot`（由 `scripts/make_minecraft_demo.py` 生成）
> 验证入口：`scripts/check_minecraft_demo.py`（重建 .blend → 导出 → 无头 Godot 真机探针）

## 1. 目标与边界

### 1.1 v1.0 要达成的结果

v1.0 范围已拍板，按以下 5 条 + 1 条边界验收；具体里程碑见 §10。

1. **闭环可玩**：采集 → 背包 → 合成 → 建造 → 存档/读档，全流程可完成且读档不丢状态。
2. **生存压力**：连续昼夜循环、夜间刷怪、近战与血量、死亡重生。
3. **地形纵深**：世界高度 64、海平面 32；洞穴、矿石分层分布、水与岩浆、树木生长；视距按区块档位（8/12/16/24/32，默认 16 区块 = 256 格），接近原版。
4. **表现层**：原版配色贴图、破坏裂纹、正确着色与雾、菜单可交互。
5. **可换内容**：一个资源包换掉全套贴图；一个数据包新增 3~5 种方块与配方；全程不改代码。
6. **多维度边界**：不做完整末地线，只做一个极简末地场景（单岛 + 虚空 + 返回门），证明多维度导出、切换与存档能跑通。
7. **工程基线**：T0/T3 的基线与指标、T1/T2 的设置与入口、T5 的视角稳定性、C1-C6 的资源包/数据包能力全部并入里程碑，不另起一套。

### 1.2 非目标

- 不做完整 1.20：红石、村庄、附魔、酿造、完整生物群系/结构生成等均不做，只实现子集。
- 不做完整末地线；极简末地只用于验证多维度导出、切换、存档，不扩展玩法；本轮不做下界。
- 不做多人/联机/网络同步。
- 不为了界面重做而引入第三方 UI 框架、网页视图或运行时 HTML。
- 不追求与参考设计稿像素级一致；只采纳其布局、层次、配色和交互反馈方式。
- 不使用受版权保护的原版素材；贴图用原版配色的程序化近似，资源包示例也必须是自制素材。
- 不手工修改任何生成物（`.blend`、`我的世界_godot/**`、`game_logic_*.gd`、`.tscn`）。生成物只能由生成器重建。
- 示例线（T*/E*）不修改 `BlenderGameKit/`；只有 T5 拿到明确证据指向框架/codegen 缺陷时才例外，且必须先补单测、走独立审批。
- 本体线（C*）只修改 `BlenderGameKit/` 与 `tests/`，不修改 `scripts/make_minecraft_demo.py`、`scripts/check_minecraft_demo.py`，不重建或手改 `examples/demo_minecraft/**`。
- 本体线不实现背包/合成 UI，也不直接改 demo；数据包只提供数据模型、校验与运行时查询接口，demo 接入由示例线任务完成。

### 1.3 完成定义（DoD）

- `python scripts\check_minecraft_demo.py` 输出 `MINECRAFT_CHECK=OK`。
- 新增指标探针输出可对比的基线/结果数据，且阈值达标（见 §5）。
- 关键流程有真机证据：真窗口截图（1280×720、1920×1080）+ 无头探针断言。
- 所有改动都落在生成器脚本或检查脚本里；重新生成后产物可复现。
- 本体线的资源包/数据包在最小 fixture 工程与 demo 只读副本上通过集成矩阵；demo 重新生成后不出现行为回退。
- 导出产物带核心版本戳，示例线能检测"构建过期"并按 §3.4 的矩阵安排复测。
- 文档（README、生成器 docstring、`docs/待办清单.md` 本轮记录）与最终行为一致。

### 2.2 已确认的缺口与风险

1. **空种子不是随机**：新建面板占位符写「留空 = 随机」，但 `_on_create` 原样写入空串（`make_minecraft_demo.py:1486`），区块脚本 `_hash_string("")` 恒为 0（`:468-482`），所有空种子世界完全相同，且存档里是空串，无法复现。
2. **世界大小语义不清**：`WORLD_SIZES = [0, 128, 256, 512]`（`:156-157`）在 `_replan` 里是"距原点半径"（`:247-250`），UI 文案却是「128 格」。已决策按边长显示（Q1），实现见 T1/T7。
3. **渲染距离档位表有两份**：区块脚本 `RADIUS_STEPS`（`:154-155`）与设置脚本硬编码 `[10, 14, 18, 22]`（`:1914-1923`），改动时容易漏一处。
4. **视距小、地形刷出**：
   - `BUILD_PER_FRAME = 1`（`:153`），`_step_build` 一帧只建 1 列（`:267-273`）；
   - 换格时立即把范围外的列卸载（`:254-261`），没有提前建；
   - 视距档位上限 22、默认 14（`:154-155`、`:3409-3410`）。
5. **每方块 3 个节点**：`_build_column` 每块都新建 `StaticBody3D + CollisionShape3D + MeshInstance3D`（`:276-334`），且每块新建一个 `BoxShape3D`（`:319-322`）、每块接一个 `tree_exiting` 信号（`:333`）。默认 14 格时场上约 2000+ 方块节点。
6. **周期性全场景扫描**：`_cull_placed` 每 0.25 秒遍历场景内所有 `StaticBody3D`（`:519-531`），地形多时是固定尖峰。
7. **开始界面仍是静态图**：`_build_menu_bg` 直接铺 `mc_menu_bg.png`（`:1111-1127`），贴图由 `ensure_menu_background` 生成（`:2873-2877`），没有动画、没有按钮反馈、没有键盘导航。
8. **文案过期**：`examples/demo_minecraft/README.md:8-10` 仍写「开始游戏 / 创建游戏」，与现状不符。
9. **存档名与世界名可能分叉**：保存面板允许改名（`:1463-1472`），但 `world_settings.name` 取的是 `世界名`（`:1549-1550`）。已决策两者不同步（Q5），需在 UI 与文档写明各自含义。
10. **旧档兼容没有 fixture 测试**：只有读档时的默认值回退（`:1599-1609`），没有"旧格式存档文件"回归样本。

### 2.3 本体线现状（资源包 / 数据包）

现有可复用的挂点：

| 能力 | 位置 | 现状 |
|---|---|---|
| 着色器分发 | `BlenderGameKit/asset_export.py:12782-12790` | 把插件 `shaders/*.gdshader` 复制进项目 `shaders/`，并按需生成剔面变体 |
| 着色器变体追踪 | `BlenderGameKit/generated_files.py:70-92` | 清理链认识插件着色器名，避免误删/漏删 |
| 材质生成 | `BlenderGameKit/asset_export.py:10497-10678` | 生成 `.tres` 并写 `ShaderMaterial`，路径写死 `res://shaders/...` |
| 材质覆盖点 | `BlenderGameKit/asset_export.py:8030-8064` | 已有按节点/表面的 `material_override` / `surface_override` 机制 |
| autoload 注册 | `BlenderGameKit/asset_export.py:6278-6320`、`6460-6526` | `GkMainUi` / `GkPlayerPrefs` 的注册/摘除是幂等的，可直接照抄 |
| 生成物清单与清理 | `BlenderGameKit/generated_files.py:42-48`、`95-148` | 只清理插件目录；新增 `packs/` 必须显式决定"永不清理" |
| 项目布局 | `BlenderGameKit/project/layout.py:21-34` | 固定 5 个子目录 + 按需 `curves/`、`audio/`；没有 `packs/` |
| 打包发布 | `BlenderGameKit/packaging.py:1-120` | 只负责导出预设与 `--export-release`，资源随工程打包 |
| 测试 | `tests/test_codegen.py`、`tests/blender_smoke.py` 等 | 纯 Python 单测 + Blender 冒烟，未见资源包/数据包测试 |

已确认的本体线缺口：

1. **没有"包"抽象**：着色器/材质/贴图只能是插件内置或用户手改，缺少"按包 id 覆盖、可开关、可追溯"的层。
2. **覆盖没有优先级**：`asset_export` 直接写死 `res://shaders/gk_toon*.gdshader`，没有"内置 < 包 < 单物体"的解析链。
3. **方块/物品/配方写死在示例里**：示例的物品名在 `make_minecraft_demo.py:1015-1016`，方块表在地形脚本内；本体没有数据模型、校验器或运行时查询接口。
4. **没有版本戳**：生成物清单只有文件列表，示例线无法判断"这份构建是用哪版本体导出的"。
5. **新增目录会被清理链漏掉或误删**：`generated_files.GENERATED_DIRS` 不含 `packs/`，一旦导出器把包复制进 `art/`、`materials/` 就会与"用户文件不删"原则冲突。

> 结论：本体线需要先定契约（C1），再分别做资源包（C2）与数据包（C3），最后接版本戳/清理（C4）、demo 只读试验场（C5）和编辑器入口（C6）。

## 3. 任务分解与排序

### 3.1 依赖图（v1.0 里程碑顺序，任务级细节见 §10）

```
M0 基线/契约/稳定性
   └─> M1 闭环：采集 → 背包 → 合成 → 建造 → 存档
          └─> M2 地形纵深 + 区块视距（默认 16 区块 = 256 格）
                 └─> M3 生存：昼夜/刷怪/近战/死亡重生
                        └─> M4 表现层：贴图/裂纹/着色雾/交互菜单
                               └─> M5 可换内容：资源包 + 数据包
                                      └─> M6 多维度 + 收尾发布

本体线（可与 L1 并行）：
C1（M0 契约）→ C3（M2 数据包运行时）→ C2（M4 资源包）→ C4/C5/C6（M5 集成与入口）
```

说明：
- **§10 是 v1.0 的权威顺序**；本节后续 T/C 任务表保留为任务卡索引。
- 里程碑内仍遵守 §3.3 的单写者与文件所有权；跨里程碑不跳过验收。
- 本体线 C2/C3 可以在示例线 M2/M3 期间并行开发，但 C5 集成必须等 M4 的构建，C4 必须在 C2/C3 之后。
- 原 `T0→T8` 的顺序已被里程碑重排：T2 前移到 M0，T4 拆为 T4a/T4b，T5 移到 T4a 之后、T4b 之前，T6/T7 移到 M4，T8 移到 M6。映射见 §10.3。

### 3.3 并发与冲突控制（硬规则）

#### 3.3.1 五条 lane

- **W-example（示例线编码方）**：唯一允许修改 `scripts/make_minecraft_demo.py`、`scripts/check_minecraft_demo.py`、`examples/demo_minecraft/**` 的角色。线内同一时刻只允许 1 人（S-INV 也必须排队）。
- **W-core（本体线编码方）**：唯一允许修改 `BlenderGameKit/**` 与 `tests/**` 的角色。线内同一时刻只允许 1 人。
- **R lane（审查/研究方）**：只读。只允许写 `.audit/minecraft/reviews/`、`.audit/core/reviews/`、`.audit/*/design/`。禁止改源码、禁止重建产物。
- **G-example（示例线门禁）**：跑 `check_minecraft_demo.py` 会重建 `examples/demo_minecraft/**`。同一时刻只允许一个，且必须持有 W-example 锁。
- **G-core（本体线门禁）**：只跑纯 Python 单测、Blender 冒烟、`_dist/core_pack_probe` fixture；不得重建 demo，不得写 `examples/**`。

#### 3.3.2 写锁协议（两把线锁 + 一把文档锁）

1. 示例线锁：`.audit/minecraft/writer.lock`；本体线锁：`.audit/core/writer.lock`。
2. 获取：仅当对应锁不存在时创建，内容为：任务号、操作者、开始时间、本任务将改动的文件 SHA256 列表。
3. 释放：完成任务卡 + 门禁 + 交接记录后删除。
4. 冲突：同一条线锁存在时，任何编码方必须停止并询问，不得"先改一点"。
5. 过期接管：锁超过 2 小时，接管者必须先核对锁内 SHA256 是否与磁盘一致；不一致则停止并升级给用户。
6. **跨线任务**（必须同时改两条线文件，例如集成失败后改核心再改 demo）：按固定顺序先取本体线锁、再取示例线锁，合并为一张任务卡执行；不得两人各改一半。
7. 文档锁：`docs/待办清单.md` 与 `docs/plans/**` 共用 `.audit/docs.lock`；只允许追加本轮记录，不允许并发改同一段。
8. 每个任务结束写交接记录：`.audit/minecraft/handoffs/` 或 `.audit/core/handoffs/`，含哈希、命令、指标、失败项。

### 3.4 线间接口契约与复测矩阵

#### 3.4.1 接口契约（C1 冻结，后续只加不改）

1. **包目录**：`packs/<pack_id>/pack.json`，字段至少含 `id`、`version`、`api_version`、`type`（`resource`/`data`/`both`）、`overrides`、`data`。
2. **资源覆盖**：导出期解析（烘焙），优先级 `内置默认 < 资源包 < 单物体覆盖`；生成 `.tres` 时直接引用 `res://packs/<id>/...`，**不复制进 `art/`、`materials/`、`shaders/`**，避免与生成物清理链争所有权。
3. **数据包**：`packs/<id>/data/blocks.json`、`items.json`、`recipes.json`；ID 为稳定字符串 `"<pack_id>:<name>"`，禁止用数组下标做持久化标识。
4. **运行时**：数据包由 autoload `GkData` 加载；无数据包时不注册 autoload；移除包时必须摘掉 `[autoload]` 旧行（照抄 `ensure_player_prefs_autoload` 的幂等做法）。
5. **版本戳**：每次导出在 `.gk_export_files`（或 `project.godot` 的 `[gk]` 段）写 `core_version`、`pack_ids`、`pack_hashes`；示例线 `--no-rebuild` 用它对当前核心版本与包列表做过期检测。
6. **存档**：示例线若持久化物品，只写 ID 与 `pack_version`，不写索引；旧档缺字段按默认值读。
7. **安全**：包内只有 JSON/文本/图片，不执行脚本；路径必须相对、禁止 `..` 与绝对路径；JSON 有大小上限与字段白名单。

#### 3.4.2 复测矩阵

### T4 地形视距 / 刷出 / 帧率（P1）

**目标**：走动时视距内不出现"一块块刷出"，帧时间稳定；T4a 维持当前档位，区块视距在 T4b 做。

**改动范围**：生成器内 `CHUNK_SCRIPT`、`RADIUS_STEPS`、`WORLD_SIZES` 注释、变量默认值、创建/设置面板档位。

**实施要点（按顺序，逐项验证）**
1. **预建 + 迟滞（先做，收益最大）**
   - 把"可见半径"与"保留/预建半径"分开：`_radius` 为可见，保留半径 = `_radius + 3`，预建半径 = `_radius + 1`。
   - 换格时只卸载超出保留半径的列；预建半径内的列提前排队。
   - 队列优先级：先距离，再按玩家速度方向加权（朝行进方向先建）。
   - 目标：默认 14 格时，一帧 1 列即可在玩家到达前 3 格完成预建，先证明不刷出，再谈加视距。
2. **降低单列成本（在预建之后做）**
   - 共享一个 `BoxShape3D` 实例，避免每块 new。
   - 评估"每列合并网格"：保留每块的独立碰撞体（保证逐块挖），把视觉合并成每列 1 个 `MeshInstance3D`；挖掉一块后只重建该列视觉。
   - 预估收益不足或风险过高时，允许只做共享形状 + 去掉不必要的每块信号，记录数据后再决定。
3. **消除周期性扫描**
   - `_cull_placed` 改为维护"放下的方块"节点表，不再每 0.25 秒遍历全场 `StaticBody3D`。
4. **视距档位（T4a 不动，T4b 按 Q12 执行）**
   - T4a 保持当前档位，先证明预建不刷出。
   - T4b 档位 `8/12/16/24/32` 区块 = 128/192/256/384/512 格，默认 16 区块（256 格）；同步创建面板、设置面板、变量注释、探针断言。
   - 旧档存的是索引，索引含义变化只影响视距，不影响地形与改动，记录到兼容说明。
   - 性能不达标按 16→12→8 回退，每次回退需用户确认并记录。
5. **边界观感**
   - 确认雾在可见边界之前开始，屏幕内不出现硬切边；必要时只调雾，不调地形算法。

**验收标准**
- AC-T4-1：三处档位表逐项相等，默认值一致。

- AC-T4-3：同机同构建对比 T3 基线，`frame_p99_ms ≤ 25`、`frame_max_ms ≤ 50`，且无 >100ms 的帧；若机器基线本身更高，按"p99 相对改善 ≥30%"判定。

**不做**：不改地形高度算法、不改树木生成规则、不引入多线程网格生成（除非数据证明必要且另行评审）。

**风险/回滚**：

### C2 资源包：shader / 材质 / 贴图覆盖（P0）

**目标**：导出的材质能按资源包解析并引用包内 shader/贴图，默认无包时产物与现在逐字节一致。

**前置**：C1。

**改动范围**：新增 `BlenderGameKit/pack_resources.py`（纯标准库解析/解析链）；改 `BlenderGameKit/asset_export.py` 的材质/着色器路径生成；改 `BlenderGameKit/godot_look.py` 中材质参数来源（如有必要）；`BlenderGameKit/project/layout.py` 增加 `PACKS_DIR`（**不进 `SUBDIRS`**，按需创建）；新增 `tests/test_pack_resources.py`。

**实施要点**
1. 解析链集中到一个函数：输入"逻辑 shader 名 / 材质名 / 贴图名 + 场景 + 包根目录"，输出最终 `res://` 路径与来源说明；所有材质生成点只调它。
2. 覆盖在**导出期烘焙**：生成的 `.tres` 直接引用 `res://packs/<id>/...`；不把包文件复制进 `art/`、`materials/`、`shaders/`，避免清理链争所有权。
3. 贴图覆盖只改引用路径，不复制、不改尺寸、不做运行时替换。
4. 材质参数覆盖按 C1 白名单字段写入 `.tres`；未列字段忽略并记 warning。
5. 无包/包无效/字段缺失时回退内置默认，导出继续，报告里列出回退原因。
6. 导出报告增加"资源包"小节：包 id、版本、覆盖了哪些逻辑名。
7. 默认路径零变化：提供 golden 测试，断言无包时生成的 `.tres` 与基线逐字节一致。

**验收标准**
- AC-C2-1：无资源包时，样例场景生成的 `.tres`/`.gdshader` 引用与基线完全一致（golden diff = 0）。
- AC-C2-2：有资源包时，`.tres` 引用 `res://packs/<id>/...`；包目录内文件零写入（哈希不变）。
- AC-C2-3：优先级测试覆盖 内置/包/单物体 三层，结果符合 C1 表。
- AC-C2-4：损坏 manifest、缺失 shader、重复逻辑名、`../` 路径、超大 JSON 均按 C1 策略处理，导出不崩。

- AC-C2-6：纯 Python 单测全绿；未改 demo 生成器与产物。

**不做**：不做运行时热替换 shader、不做材质编辑器、不做贴图压缩/格式转换。

**风险/回滚**：`asset_export.py` 体量大，改路径生成可能波及默认导出。对策：先加"解析函数 + golden 基线测试"，接线只改 2~3 个生成点；失败按文件备份恢复 `asset_export.py`、`godot_look.py`、`layout.py` 与新增模块。

### C3 数据包：方块 / 物品 / 配方 + 运行时（P0）

**目标**：数据包 JSON 能在 Godot 运行时被校验、加载、查询；无包时不产生任何全局单例。

**前置**：C1。

**改动范围**：新增 `BlenderGameKit/pack_data.py`（schema 校验，纯标准库）；新增 GDScript 模板（`scripts/gk_data.gd` 内容，建议放 `BlenderGameKit/pack_runtime.py` 或 `script_assets.py`）；`BlenderGameKit/project/layout.py`；autoload 注册逻辑（参照 `asset_export.ensure_player_prefs_autoload`）；`tests/test_pack_data.py` + `tests/fixtures/packs/**`。

**实施要点**
1. 运行时 `GkData` autoload：只读加载 `packs/*/pack.json` 中 `type` 含 `data` 的包；暴露 `get_block(id)`、`get_item(id)`、`recipes_for(item_id)`、`all_block_ids()`、`all_item_ids()`、`pack_meta()`。
2. 注册/摘除幂等：有数据包才写 `[autoload]`；删除包后必须摘掉旧行，避免 Godot 启动报 "Failed to instantiate an autoload"。
3. 校验：必填字段、类型、重复 ID、悬空引用（recipe→item）、未知字段、文件大小、路径安全；错误带 `文件:字段` 与包 id。
4. 失败策略：坏条目丢弃并 `push_error`，其余条目可用；整包不可读时 `GkData` 仍存在但为空，游戏能启动。
5. 确定性：ID 排序、字典只读副本；同一包重复加载结果一致。
6. 存档接口：只给稳定字符串 ID 与 `pack_version`，不假设任何物品索引。
7. 测试：纯 Python 校验器单测 + fixture 工程 headless smoke（有包/无包/坏包/移除包）。

**验收标准**
- AC-C3-1：fixture 工程有数据包时 `GkData` 存在，`all_block_ids/all_item_ids` 数量与黄金样例一致，`get_*` 可查。
- AC-C3-2：无数据包时 `project.godot` 无 `GkData` autoload，工程可启动。
- AC-C3-3：移除数据包后旧 autoload 行被摘掉，工程可启动。
- AC-C3-4：重复 ID、悬空 recipe、损坏 JSON、缺失文件、`../` 路径均按 C1 策略处理；游戏不崩，诊断可定位。

- AC-C3-6：`recipes_for` 只返回有效配方；引用缺失物品的配方被丢弃并记录。
- AC-C3-7：纯 Python 单测全绿；未改 demo 生成器与产物。

**不做**：不做背包 UI、不做合成台交互、不做配方执行逻辑、不改示例存档。

**风险/回滚**：autoload 注册错误会让整个工程起不来。对策：照抄现有 `ensure_*_autoload` 的幂等实现；每次 smoke 都覆盖"移除包"路径；失败恢复 `asset_export.py`/`layout.py` 与新增模块，并删除 fixture 工程的 autoload 行。

### 5.2 指标定义（T3 建立；T4a 起逐步作为门槛，M2 起以 §10.6 为准）

| 指标 | 定义 | 目标（同机同构建对比） |
|---|---|---|
| `frame_p99_ms` | 测量段每帧 delta 的 99 分位 | T4a：≤ 25ms 或相对基线改善 ≥30%；M2 起：≤ 16.7ms |
| `frame_max_ms` | 最大单帧 | ≤ 50ms；无 >100ms |
| `queue_drain_frames` | 跨格后新队列清空所需帧 | ≤ 预建提前量对应的帧数（默认 1 列/帧时 ≈ 3 格 × 帧/格） |
| `missing_near_cells` | 玩家 10 格内缺失列的最大连续帧数 | 0 |
| `cells` | 当前保留列数 | 与半径表一致；相对基线增长 ≤40%（视距提升后） |
| `nodes_static/mesh/shape` | 场景节点统计 | T4a 阶段合并网格后相对基线下降 ≥40%；M2 起改用 `draw_calls`/`rss_mb` |
| `draw_calls` | 每帧 draw call 数 | M2 起：L3 观察项，≤ 3500 且 ≤ 8 区块基线的 1.5 倍（Q17，见 §11.7）；不做绝对 800 门槛 |
| `rss_mb` | 峰值常驻内存 | M2 起 ≤ 2048 |
| `chunk_build_ms` | 单帧区块构建耗时 | M2 起 p99 ≤ 4ms/帧 |
| `cold_start_s` | 进程启动到主菜单可交互 | M2 起 ≤ 3s |
| `world_load_s` | 点击开始/读档到可操作 | M2 起 ≤ 5s（16 区块） |
| `chunk_rebuild_count` | 卸载迟滞区内往返触发重建次数 | 0 |
| `unload_deferred_chunks` | 超过加载边界但仍保留的区块数 | ≤ 迟滞环容量（2 区块） |
| `save_size_mb` | 万次改动存档体积 | M2 起 ≤ 5MB |
| `menu_p99_ms` | 菜单静止 3 秒帧时间 p99 | ≤ 20ms |
| `menu_node_growth` | 菜单开合 10 次后背景子节点增量 | 0 |

> T4a 仍允许用旧阈值（25ms/节点数）证明"旧架构下不再刷出"；T4b 起以 §10.6 的区块视距预算为准（默认 16 区块 = 256 格），二者不要混用。

## 7. 回滚手册

### 7.1 总原则

1. 每个任务开始前备份：示例线备份 `make_minecraft_demo.py`、`check_minecraft_demo.py` 到 `.audit/minecraft/backups/<task>/`；本体线备份本任务将改动的 `BlenderGameKit/**`、`tests/**` 文件到 `.audit/core/backups/<task>/`。
2. 回滚按任务逆序进行（后做的先回滚），避免把后续依赖一起带掉。
3. 回滚后必须：重建 → 对应门禁 → 记录结果 → 更新交接记录。
4. 不手工修补生成物；回滚生成器后统一重建。
5. 本体线回滚后，如果导出行为发生变化，必须请示例线重建 demo 并跑完整门禁。

### 7.2 分级回滚

| 级别 | 场景 | 动作 |
|---|---|---|
| L1 单步回滚 | T4 的"合并网格"失败 | 只撤销该子步，保留预建/扫描优化，重跑门禁 |
| L2 单任务回滚 | 某任务验收不过 | 恢复该任务开始前的两份脚本备份，重建+门禁 |
| L3 批次回滚 | 多个任务连环失败 | 回到 T0 基线备份，重建+门禁，重新排任务 |
| L4 框架回滚 | T5 改了 `BlenderGameKit/` | 恢复框架文件 + 对应单测，重跑离线测试与门禁 |
| L5 本体线单任务回滚 | C1~C6 任一验收不过 | 恢复 `.audit/core/backups/<task>/` 中的本体与测试文件；重跑纯 Python 单测 + Blender 冒烟；通知示例线重建并跑完整门禁 |
| L6 跨线集成回滚 | C5 四组组合失败且归属不清 | 冻结两线 → 回退到最近一次双方签过 PASS 的核心版本与 demo 构建 → 重跑完整门禁与集成矩阵；不得只回退一侧后直接宣称通过 |

### 7.3 存档安全

- 读档只读用户文件，不主动改写。
- 保存前先写临时文件再替换（若当前实现是直接覆盖，T1 顺手改为临时文件 + 替换），避免半截文件。
- 探针必须继续遵守"先把用户 `user://saves` 目录整体挪走、跑完放回"的规则（`check_minecraft_demo.py:116-123`）。

1. **谁发起**：本体线完成 C2/C3/C4 后发起；示例线完成任何会影响产物结构的改动后也可发起。

### 8.5 停止与升级条件

出现以下任一情况，编码方/审查方必须停止并升级给用户，不得自行扩大范围：

- 需要示例线改 `BlenderGameKit/` 才能继续（T5 证据除外，且需先补单测）。
- 需要手改生成物才能通过验收。
- 本体线任务需要修改 demo 生成器或生成物才能完成（说明边界被突破，应拆成跨线任务并重新审批）。
- 存档兼容出现不可逆风险（旧档读失败且无回退方案）。
- 门禁在同一原因下连续失败 2 次且没有新证据。

- 构建版本戳与当前核心版本不一致，但有人要求直接判定集成通过。

### 10.6 16 区块是最大技术风险

**规模结论**

- 当前默认半径 14 格、上限 22 格；16 区块 = 256 格，半径是 18.3 倍、面积约 334 倍。
- 当前每方块 3 个节点且每块新建 `BoxShape3D`；按现架构放大到 16 区块约 67 万方块、200 万节点，必然不可行。
- 因此 T4b 不是"把数字调大"，而是架构替换。必须先出测量报告，再谈洞穴/矿脉密度。

**目标架构**

1. 区块 16×16 水平区块 + 每列多个 16 高 section（Q21），面剔除（可选 greedy）；每 section 一个 mesh，按材质合批（优先 atlas）。
2. **世界高度 64、海平面 32**（Q20），y 索引与 section 边界一次改到位；旧档迁移见 §11.10。
3. 碰撞分级：距玩家 ≤ 4 区块用 `ConcavePolygonShape3D`；4~8 区块只保留表面碰撞或不做；>8 区块无碰撞。
4. **先加载后进入**：进入世界前构建出生点周围 5×5 区块（80×80 格）的地形、网格与碰撞，加载界面显示进度与档位；加载未完成不得把玩家放进世界。
5. **卸载迟滞**：加载边界与卸载边界分离，卸载边界外扩 2 区块；迟滞区内往返不重建，离开迟滞区才释放。
6. 异步构建：worker 线程生成网格，主线程每帧预算 ≤ 4ms；环形预加载按已加载环推进，不按玩家瞬移追赶。
7. 只存 diff：地形由种子确定性生成；存档只存 `(dim,x,y,z) → block_id` 改动。
8. 洞穴/矿脉在生成期写入（纵深按 64 布局，见 §11.5 M2b）；远处 chunk 可跳过洞穴细节（LOD），近处完整。

**指标（16 区块默认档位，绝对目标；T3 基线只作回归对照）**

> ⚠ 本表已被 2026-11-11 实测部分推翻（1736 draw calls 仍 155fps、真正瓶颈是 4.3s 建列）；**口径以 §11.7 为准**，本表保留作原始目标记录。

| 指标 | 目标 | 测量条件 |
|---|---|---|
| 帧时间 p99 | ≤ 16.7ms | 1920×1080，16 区块，连续移动 60s |
| 帧时间 max | ≤ 50ms | 同上 |
| draw calls | ≤ 800 | 同上 |
| 峰值内存 RSS | ≤ 2GB | 加载完成后 + 连续移动 10 分钟 |
| 单帧区块构建 p99 | ≤ 4ms | 跨区块移动 60s |
| 进入世界加载 | ≤ 5s | 点击开始/读档到可操作 |
| 冷启动到主菜单 | ≤ 3s | 进程启动到菜单可交互 |
| 加载后近处缺失列 | 0 | 进入后前 120 帧 |
| 存档体积 | ≤ 5MB | 万次改动 |

**回退触发条件（独立判定）**

连续 3 次测量任一不达标即触发回退，不靠主观感受：

1. p99 > 16.7ms，或 max > 50ms；
2. draw calls > 800，或 RSS > 2GB；
3. 进入世界加载 > 5s，或单帧构建 p99 > 4ms。

回退顺序固定为 **16 → 12 → 8 区块**；每次回退记录指标、原因、影响范围，并得到用户确认（Q12）。若洞穴导致几何爆炸，洞穴只在 ≤ 6 区块内生成、远处仅表面；若 8 区块仍不达标，保留 8 区块 + 雾补偿，并明确写"未达 v1.0 视距目标"，不得静默通过。

**验收独立性**

- **先加载后进入**与**卸载迟滞**是独立 AC（M2-AC5/M2-AC6），必须各自有探针断言与证据，不得用"视距调好了"或"帧率没掉"代替。
- 探针至少记录：`world_load_s`、`missing_near_cells`、`chunk_rebuild_count`、`unload_deferred_chunks`、`draw_calls`、`frame_p99_ms`、`rss_mb`。
- 即使最终回退到 12 或 8 区块，这两项 AC 仍按原样验收。

**确定性**

- 整数哈希 + 固定采样；同种子跨运行 golden hash 一致。
- 禁止用 `randf()` 直接生成地形；树/矿脉用坐标哈希。
- 新增方块/矿石不得改变已有种子的地形哈希（除非明确接受世界重置）。

### 11.2 两条实测结论对计划的影响

**结论 1（渲染不是瓶颈）**：1280×720、下雨、朝前看、标准画质 = 155 fps，但 **1736 draw calls / 3.73M 三角面**；真正卡的是 **进世界建列 4.3 秒**。

- 原 §10.6 的 `draw calls ≤ 800` 已被实测证伪：当前视距下就有 1736，这是**未做合批的现状值**，不是退化。
- 帧时 p99 ≤ 16.7ms 在这台机器上余量很大，不能作为主要验收信号；**主门槛改为"进世界加载时长 + 单帧构建预算 + 内存 + 无卡顿感知"**，帧时降为"不得低于 60fps"的底线。
- 视距口径需重定（Q17）：**16 区块仍作为默认目标，但不再用"面积倍数"恐吓式论证**，改用"加载时长 + draw calls 相对化"。
- 这台机器 155fps 不代表目标用户；验收必须记录硬件与画质档（Q17）。

**结论 2（glTF 导出 V 翻转）**：导出会把 UV 的 V 翻一次，所有带 UV 的模型都会踩；本轮在 demo 侧绕开。

- 这是**本体线导出正确性缺陷**，登记为 **C7（P0）**，不得留在示例线的 workaround 里。
- 验收必须能识别"是否翻转"：用带方向标记的 UV 棋盘方块导出 → 在 Godot 截图/探针比对 V 方向。
- 修复后示例线的绕开代码必须删除并重导出回归（否则两层修正叠加会导致二次翻转）。

### 11.7 指标口径（已定，Q17）

**三层门槛，按重要性排序**

| 层 | 指标 | 目标 | 理由 |
|---|---|---|---|
| L1 主门槛 | `world_load_s`（点击开始到可操作） | ≤ 5s（16 区块只等 5×5） | 实测唯一真实瓶颈（当前 4.3s 建列） |
| L1 主门槛 | `chunk_build_ms` p99 | ≤ 4ms/帧 | 决定走动时是否卡顿 |
| L1 主门槛 | `rss_mb` | ≤ 2048 | 16 区块的主要物理上限 |
| L2 底线 | 帧时 p99 / max | ≤ 16.7ms / ≤ 50ms @1280×720 标准画质 | 保持 60fps，但不再作为主要信号 |
| L3 观察 | `draw_calls` | ≤ 3500，且 ≤ 8 区块基线的 1.5 倍 | 当前已 1736，绝对 800 不成立 |
| L3 观察 | 三角面 | 记录即可，不设硬门槛 | 3.73M 下仍 155fps |

**回退触发（重定）**：连续 3 次测量中 `world_load_s`、`chunk_build_ms`、`rss_mb` 任一不达标即触发 16→12；帧时只在低于 60fps 时作为附加触发。每次回退记录指标与原因并经用户确认。

**验收环境**：必须记录硬件型号、画质档、分辨率；建议补一台中端机基线，避免 155fps 机器掩盖问题。

> 高度改为 64 后，`rss_mb` 与 `world_load_s` 必须重测（体素总数约翻倍）；M2a 的测量报告以新高度为准。

### 11.10 世界高度变更与旧档迁移口径（Q20）

**变更内容**

| 项 | 旧 | 新 |
|---|---|---|
| 世界高度 | 当前高度上限约 10 格可用（max 10） | **64**（y=0~63） |
| 海平面 | 无明确概念 | **32** |
| 分段 | 无（每列整体） | **16 高 section**，每列 4 段（0-15 / 16-31 / 32-47 / 48-63） |
| 地形噪声基准 | p50 3 / p90 6 / max 10 | 按 64 重定：p50≈38 / p90≈48 / 上限 ≤60（C-E8） |

**为什么与 M2a 同批**：高度和分段共用同一套 y 索引与网格边界。先改高度再改分段 = 地形哈希、存档、碰撞各迁一次；同批只迁一次。**M1 期间禁止提前改高度，也禁止写死 256/64 或固定层数**（见 §11.5 A6）。

**迁移口径（B6）**

1. 存档新增 `world_height` 与 `sea_level` 字段；写入时写当前值。
2. 读档时若 `world_height != 64`（含缺字段的旧档）：
   - 判定为"地形不兼容"，**不尝试逐块迁移**（旧地形在 64 高体系下无法等价重建）；
   - 弹出明确提示：「此存档的世界高度为旧版本（X），地形将按新版本重新生成；背包、设置与玩家位置将保留。」需玩家确认；
   - 确认后：**只重置地形与世界改动**，保留背包/快捷栏/箱子内容（若坐标落在新地形之外则丢弃并在报告里列出数量）、世界设置、玩家血量与时间；
   - 取消则回到菜单，不写盘。
3. 读档后 `world_height` 不匹配但玩家强制进入（调试开关）时，必须打日志标记 `MIGRATION_FORCED`，探针不得当作 PASS。
4. 迁移报告写入 `.audit/minecraft/migrations/`：旧高度、丢弃物品数、重置改动数、耗时。
5. 新档不触发任何提示；`world_height` 缺失但世界改动为空的新建档按新高度处理。

**验收（B6 AC）**

1. 旧档 fixture → 读档出现提示，文案包含旧高度与新高度。
2. 确认后地形重建、背包保留、玩家不卡在方块里。
3. 取消后不写盘，存档哈希不变。
4. 新档无提示。
5. 迁移报告生成且字段齐全。
