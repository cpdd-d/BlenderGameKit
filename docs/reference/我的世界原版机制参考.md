## 1. 挖掘时间

### ① 原版怎么做（✅ 出处：[挖掘 - Minecraft Wiki](https://minecraft.fandom.com/zh/wiki/%E6%8E%96%E6%8E%98)）

**基本模型**：每个方块有一个**硬度（hardness）**。玩家按住攻击键时，每游戏刻给目标方块累积"损坏值"；损坏值 ≥ `硬度 × 30` 时方块破坏。基础速度是 1 点/刻，所以徒手（能收获时）的时间是 `硬度 × 1.5 秒`。

Wiki 给的伪代码（✅ 同页 §计算）：

```text
if (isBestTool):
    speedMultiplier = toolMultiplier
    if (not canHarvest):
        speedMultiplier = 1
    else if (toolEfficiency):
        speedMultiplier += efficiencyLevel^2 + 1

if (hasteEffect):      speedMultiplier *= 0.2 * hasteLevel + 1
if (miningFatigue):    speedMultiplier *= 0.3 ^ min(level, 4)
if (inWater and not hasAquaAffinity): speedMultiplier /= 5
if (not onGround):     speedMultiplier /= 5

damage = speedMultiplier / blockHardness
damage /= 30 if canHarvest else 100
if (damage > 1): return 0          # 瞬间破坏
ticks = ceil(1 / damage)
seconds = ticks / 20
```

**工具倍率**（✅ 同页 §挖掘工具）：

| 工具 | "损坏"速度倍率 |
|---|---:|
| 不使用合适工具 | 1 |
| 木 | 2 |
| 石 | 4 |
| 铁 | 6 |
| 钻石 | 8 |
| 下界合金 | 9 |
| 金 | 12 |
| 剪刀 | 2（羊毛 5；树叶/蜘蛛网 15） |
| 剑 | 1.5（蜘蛛网 15） |

**正确工具 vs 错误工具**（✅ 同页 §机制、§合适挖掘工具）：

- 所有可挖方块都能被**任何工具甚至徒手**挖掉，只是时间不同；硬度为负的方块（基岩、命令方块等）永远挖不掉。
- 一部分方块要求**最低工具品质**。不满足时（无论是工具类型不对，还是品质不够）：**不吃工具倍率**，破坏时间变成 `5 × 硬度` 秒（因为走 `/100` 分支；相对"正确工具可收获"的 `1.5 × 硬度` 慢 3.33 倍），**且破坏后不掉落**。
- "合适工具"和"最低品质"是两个判断：前者决定"用哪个倍率"，后者决定"掉不掉落"。但按伪代码，只要 `canHarvest` 为假，`speedMultiplier` 就会被重置为 1；所以**品质不够时，即使工具类型正确，也吃不到倍率**，时间仍是 `5 × 硬度`，且不掉落。
- 代表性硬度（✅ 各方块页信息框）：
  - 石头 **1.5**（[石头](https://minecraft.fandom.com/zh/wiki/%E7%9F%B3%E5%A4%B4)）
  - 泥土 **0.5**（[泥土](https://minecraft.fandom.com/zh/wiki/%E6%B3%A5%E5%9C%9F)）
  - 原木 **2**（[原木](https://minecraft.fandom.com/zh/wiki/%E5%8E%9F%E6%9C%A8)）
  - 煤矿石 / 铁矿石 **3**（[矿石](https://minecraft.fandom.com/zh/wiki/%E7%9F%BF%E7%9F%B3)）
  - 箱子 / 工作台 **2.5**（[箱子](https://minecraft.fandom.com/zh/wiki/%E7%AE%B1%E5%AD%90)）
  - ⚠️ 草方块（约 0.6）、沙子（约 0.5）、树叶（约 0.2）、木板（约 2）是常见值，本轮未逐页复核，引用前建议点开对应方块页确认。
- **徒手能不能挖**：能。石头徒手是 `1.5 × 5 = 7.5 秒`（错误工具走 `/100` 分支），但不掉落；用木镐是 `1.5 × 1.5 / 2 = 1.125 秒` 且掉落。
- **哪些方块需要特定工具**：石质方块/矿石通常需要镐；雪需要锹；蜘蛛网需要剑或剪刀。斧/锹/锄大多是"加速但不强制"（✅ 同页 §合适挖掘工具）。
- **挖掘进度**：进度按"当前目标方块"累积；**换目标或换手持物品会归零**（✅ 同页 §机制）。破坏一个方块后，继续按住会有约 0.25 秒的再开采延迟（同页写 0.25 秒；§瞬间破坏又写 6 游戏刻/0.3 秒，⚠️ 两处口径略有出入）。
- **移动中挖掘**：可以边跳/边游/边骑边挖，但不在 ground 上或头在水中会让速度 ×0.2（时间 ×5）（✅ 同页 §挖掘速度）。
- **创造模式**：挖掘范围 5 格，生存 4.5 格（✅ 同页 §机制）；创造是瞬间破坏。
- 附魔/状态（效率、急迫、挖掘疲劳、水下速掘）会叠乘；本文不展开，v1.0 也用不到。

> 🔶 我们的 `HARDNESS` 更像"策划手感的秒数"，不是原版硬度。比如石头 1.2s ≈ 木镐（1.125s），箱子/工作台 0.8s 比原版铁斧（0.625s）稍慢、比徒手（3.75s）快很多。如果目标是"像原版"，应改成"硬度表 + 工具倍率 + 品质表"，而不是继续调这张秒数表。

### ③ 能落地的简化版本

1. **把 `HARDNESS` 拆成 `BLOCK_HARDNESS`（原版硬度）和 `TOOL_SPEED`（当前手持倍率）**：
   - 满足最低品质（或方块不要求工具）：`break_time = hardness * 1.5 / speed`；
   - 方块要求工具、但品质/类型不满足：`break_time = hardness * 5`（不吃倍率，且不掉落）；
   - `speed` 默认 1，木 2、石 4、铁 6（v1.0 只做到铁即可）。
2. **加一张 `REQUIRES_TOOL` 表**：石头/矿石要求"镐 + 最低品质"，不满足时仍然能挖（时间按 `5×硬度`），但 `block_mined` 不发物品。这样不用做完整工具耐久，也能还原"徒手挖石不掉落"的核心体验。
3. **加 `on_ground` / `head_in_water` 两个乘数**（0.2），用 `CharacterBody3D.is_on_floor()` 和相机是否在水体 AABB 内判断即可。
4. **换手持物品时调 `_reset_mine()`**，一行就能补齐归零规则。
5. **破坏后 0.25s 冷却**：加一个 `_mine_cooldown = 0.25`，和现有创造冷却复用。
6. 挖掘范围按模式取 4.5/5.0；把 `_mine_step` 里的 `5.0` 换成变量即可。
7. 工具耐久、附魔、时运/精准采集**不做**——v1.0 没有这些系统，硬加会拖垮背包/存档。

### ④ 对应任务

- **E1（方块/物品注册表、掉落表）**：硬度、工具类型、最低品质、掉落物都应进注册表，而不是散在脚本里。
- **E2 / M1-R（配方与工具）**：计划里 M1 要补"木/石镐、木/石剑"（见 [总体计划 L1150](file:///d:/BlenderGameKit/docs/plans/%E6%88%91%E7%9A%84%E4%B8%96%E7%95%8CDemo_%E6%80%BB%E4%BD%93%E8%AE%A1%E5%88%92_2026-11-10.md#L1150)），工具倍率正好挂在这里。

## 2. 放置规则

### ① 原版怎么做（✅ 出处：[方块](https://minecraft.fandom.com/zh/wiki/%E6%96%B9%E5%9D%97)、[潜行](https://minecraft.fandom.com/zh/wiki/%E6%BD%9C%E8%A1%8C)、[Slab](https://minecraft.fandom.com/wiki/Slab)）

- **网格与贴面**：方块对齐 1 立方米网格（✅ 方块页 §行为）。放置时，游戏先对视线做射线，命中某个方块的**某个面**，目标格 = 命中格 + 该面的法线；所以**不能凭空点在空气里放**。可替换方块（高草/矮草、雪层、水等）是例外，可以直接替换。
- **不能放进玩家/实体**：放置前会检查目标格的碰撞箱是否与实体重叠；重叠则拒绝（✅ 这一点在 Mojira 的放置碰撞报告里被反复引用，例如 [MC-116877](https://bugs.mojang.com/browse/MC-116877)、[MC-221256](https://bugs.mojang.com/browse/MC-221256)；⚠️ 具体"检查哪些实体、用默认状态还是实际状态"版本间有差异）。
- **交互方块与潜行**：对着箱子/熔炉/工作台按使用键，默认是**开界面**而不是放方块；**按住潜行**时，使用键优先"使用手上的物品"，于是可以把方块/火把放在这些方块上（✅ 潜行页 §效果："Pressing use prioritizes using a held item over interacting with a targeted block... placing a hopper on a chest, a torch on a furnace"）。
- **朝向与半砖**：台阶可以占上半格或下半格（✅ Slab 页 §Placement）：
  - 放在方块顶面，或点在侧面**下半部** → 下半砖；
  - 放在方块底面，或点在侧面**上半部** → 上半砖；
  - 同种上下半砖叠在同一格 → 双半砖；
  - 不同种类不能叠。
  - 楼梯/原木/告示牌等还有水平朝向，通常由玩家朝向或点击面决定。
- **距离**：Java 生存 4.5 格、创造 5 格（✅ 挖掘页 §机制，和放置共用交互距离）。
- **放置消耗**：生存模式从背包扣 1 个；创造不扣。

### ② 我们当前实现与它的差距

核心算法在 [can_place_here()](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1303-L1345)：

- 目标格：`base = floor(hit - normal * 0.5)`，`cell = base + normal`；再校验 `|cell - base| == 1`（[L1322-L1328](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1322-L1328)）。算法和原版一致，能正确处理角上偏格。
- 占用检查：用 0.9 立方在目标中心做 `intersect_shape`，**只把 `StaticBody3D` 当阻挡**（[L1339-L1344](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1339-L1344)）。
- 玩家本体是 `CharacterBody3D`（[L2011](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L2011)、[L2685](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L2685)），所以**不会被占用检查拦住**——也就是可以贴着/放进自己身体放方块。这是和原版最明显的规则差异。
- 右键对着箱子/工作台时，先尝试 `try_open_chest()` / `try_open_craft()`，成功就这次不放（[L1307-L1316](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1307-L1316)）。没有"潜行时优先放置"的分支。
- 放置射线是 6.0 格（节点图 [L6828-L6830](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L6828-L6830)），比原版 4.5/5 长。
- 放置消耗：`consume_current()` 生存扣 1、创造跳过（[L4531-L4548](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L4531-L4548)），节点图在创建实例前调用（[L6917](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L6917)）。这部分是对的。
- 方块种类只有整块（草/石/沙/木/叶/工作台/箱子，[L221-L229](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L221-L229)），**没有半砖、楼梯、朝向状态**。

**差距清单**：

| 项 | 原版 | 我们 |
|---|---|---|
| 必须贴面 | 是 | 是（已经对了） |
| 放进玩家 | 拒绝 | **允许**（只查 StaticBody） |
| 放进怪物/羊 | 拒绝 | 允许（CharacterBody 不查） |
| 潜行越过交互 | 可以对着箱子放方块 | 右键箱子永远开箱，没有潜行分支 |
| 半砖上下半 | 按点击面的上半/下半决定 | 没有半砖 |
| 方块朝向 | 楼梯/原木/告示牌有 | 只有整块，无朝向 |
| 交互距离 | 4.5 / 5 | 放置 6.0；开箱/合成 4.5 |
| 可替换方块 | 草、雪、水等可被替换 | 没有可替换概念 |

> 🔶 "放进自己身体"在原版里是明确的拒绝路径；我们的 0.9 立方查询其实已经能查到 `CharacterBody3D`，只是最后一步过滤掉了。修起来很小：把 `collider is StaticBody3D` 改成"任何带碰撞的 `CollisionObject3D`，但排除被放置的方块自身"。

### ③ 能落地的简化版本

1. **修占用检查**：`intersect_shape` 结果里，只要 `collider is CollisionObject3D`（玩家、羊、怪物、地形都算）就拒绝；如果担心把"要放置的资产源"算进去，按 `gk_placed`/名字排除。这样就能还原"不能放在玩家体内"。
2. **加潜行分支**：`Input.is_key_pressed(KEY_SHIFT)` 时，`can_place_here()` 跳过开箱/开合成，直接走放置流程。原版的潜行还有"不会掉下边缘"等效果，v1.0 不需要一起做。
3. **可替换方块**：只做"草方块顶部的草/雪"太复杂；v1.0 可以不做，保持"必须打到实体面"。
4. **半砖/楼梯**：如果一定要做，最小方案是给方块加一个 `shape` 字段（`full` / `slab_bottom` / `slab_top`），放置时按 `hit.y - floor(hit.y)` 判断上半/下半，碰撞盒和网格各做两套。**但这会牵动存档、区块重建、放置消耗、合成配方**，不建议塞进 M1/M2a。
5. **距离统一成常量**：`REACH_SURVIVAL = 4.5`、`REACH_CREATIVE = 5.0`，放置/挖掘/开箱都读它，避免 5.0/6.0/4.5 三个值各写各的。

### ④ 对应任务

- **E3（放置消耗、非法位置拒绝、与背包数量联动）**：这是主任务。玩家/实体碰撞属于"非法位置"的一部分，建议并入 E3 的验收，不新开任务。
- **半砖/朝向**：不在 v1.0 的 M1~M6 任务卡里，也不在 §1.2 的目标内；如果要做，属于"方块状态/形状"扩展，建议挂 M4/M5（内容扩展）时再评估，不要插进 M2a。
- **T4c 的身高/落差约束**与此无关，但放置高度上限要跟 `_terrain_ceiling`/M2a 的 `WORLD_HEIGHT` 对齐。

## 3. 区块与视距

### ① 原版怎么做（✅ 出处：[区块](https://minecraft.fandom.com/zh/wiki/%E5%8C%BA%E5%9D%97)、[选项（渲染距离）](https://minecraft.fandom.com/zh/wiki/%E9%80%89%E9%A1%B9)、[模拟距离](https://minecraft.fandom.com/zh/wiki/%E6%A8%A1%E6%8B%9F%E8%B7%9D%E7%A6%BB)）

- **尺寸**：区块 = 16×16 格。主世界高 384（Y=-64~319），下界/末地 256；内部按 16 高分成 section（✅ 区块页 §生成；section 是 1.18 后的实现细节，⚠️ 页面没逐条展开）。
- **加载/卸载**：Java 用**加载等级 0~45** 管理：>44 立刻卸载；≤31 实体计算；32 方块计算；33 完全加载；≥34 不可访问（只跑世界生成）（✅ 区块页 §Java版）。
- **渲染距离**：控制"多少区块可见"。范围 **2~32 区块**；64 位 Java（≥1GB 内存）默认 **12**，32 位默认 **8**；最大 32，其他情况 16（✅ 选项页 §渲染距离）。渲染距离是**半径**，可见区块数是 `(2d+1)²`（选项页表格）。
- **模拟距离**：单独一档，控制实体/方块刻/液体刻。Java 范围 **5~32**（✅ 模拟距离页 §模拟距离范围）；默认值随设备/版本不同（常见单人高配 12、低配 8、多人 10，⚠️ 具体以版本选项为准）。模拟距离 ≤ 渲染距离。
- **玩家移动时怎么避免"边走边长"**：
  - 客户端在进入世界前会先加载**出生点附近 43×43 区块**（✅ 区块页 §生成），并显示加载界面；
  - 渲染距离本身是"提前一圈"的：玩家看到的最远地形在渲染距离边缘，而不是脚边；
  - 区块生成是异步任务队列，按距离优先级排队，主线程只做已生成区块的网格构建（⚠️ 这部分是 1.13+ 的实现，wiki 没有逐行说明；🔶 我的概括）。
- **卸载迟滞**：⚠️ 我没有在 Wiki 找到"固定多留 N 个区块/多少秒"的官方参数。Java 的实际做法是 **ticket + 加载等级传播**：玩家标签给一个正方形范围加载等级 31，超出传播范围后等级 >44 就卸载；区块生成/光照未完成的区块会被 pending task 暂时留住（Mojira 上能看到相关讨论，如 [MC-224894](https://bugs.mojang.com/browse/MC-224894)）。所以原版更像"用 ticket 生命周期自然形成缓冲"，而不是给每个区块加一个固定迟滞。🔶 我们的"多留 2 个区块"是工程近似，不是原版参数。
- **雾**：最远地形会淡入天空色，避免硬边（✅ 选项页 §渲染距离）。这也是我们把雾和视距绑一起的依据。

6. **不要做**：后台线程构建、区块 LOD、光照传播。这三样在 Godot 单人 demo 里收益低、风险高；M2a 的验收是"16 区块可玩 + 无缺列 + 前 120 帧不刷出"，不是"和原版一样"。

## 4. 地形生成

### ① 原版怎么做（✅ 出处：[生物群系](https://minecraft.fandom.com/zh/wiki/%E7%94%9F%E7%89%A9%E7%BE%A4%E7%B3%BB)；⚠️ 1.18 细节见下）

- **1.18 之前**：主要是"高度图 + 多倍频噪声 + 生物群系噪声"。多倍频（octave）就是把不同频率/振幅的噪声叠起来：低频决定大陆/山地，高频决定小起伏。这是"多倍频"的通用含义，✅ 可在生物群系页看到"海拔高度/温度/湿度"的描述。
- **1.18 起**：地形由 **5 个气候参数**（temperature、humidity、continentalness、erosion、weirdness）+ **3D 密度噪声** 决定；continentalness/erosion 通过 **spline** 映射成"高度偏移"和"垂直拉伸"，所以能出悬崖、台地、峡湾；生物群系由同一组气候参数查表得到，形成"地形和群系软绑定"（⚠️ 这套细节在 Wiki 的 `World generation` 页，本轮抓取为空；以上来自我对 1.18 worldgen 的了解 + 二手资料，引用前建议复核 [World generation](https://minecraft.fandom.com/wiki/World_generation)）。
- **海平面**：主世界海平面 Y=63（⚠️ 1.18 后的常见值；不同版本/世界类型可能不同，引用前复核）。
- **高度与群系**：群系决定地表方块（草/沙/雪/泥等）、温度/湿度、树木种类、降水类型（✅ 生物群系页；森林/平原页的"主要方块"与"树木比例"）。海拔会影响温度，进而影响降雨/降雪（✅ 降雨页：温度每升高 1 米降 0.0016，低于 0.15 变雪）。
- **噪声类型**：原版用的是 Perlin/Simplex 系的梯度噪声，不是"每格哈希 + 双线性插值"的值噪声；后者更便宜，但高频细节的"方向性"更弱（🔶 这是实现差异，不是 Wiki 事实）。
- **3D 密度**：1.18 的洞穴、悬空地形来自 3D 密度函数，不再只是"高度图 + 洞穴 carving"；这让"地下"和"地表"共用一套形状（⚠️ 同上，需复核）。

### ② 我们当前实现与它的差距

核心在 [CHUNK_SCRIPT 的地形段](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1151-L1267)：

- `_noise01(x, z, period, salt)`：世界坐标采样 + smoothstep 双线性插值的**值噪声**（[L1169-L1182](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1169-L1182)）。
- `_height_at()` 四层叠加（[L1185-L1236](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1185-L1236)）：
  - 64 格 = 大陆（continent）
  - 19 格 = 丘陵（hills）
  - 6 格 = 小起伏（detail）
  - 2 格 = 毛边（fine）
  - 另有 80 格 `zone` 噪声做"山地/平原"分区，`mountain`/`plain` 用 smoothstep 塑形；
  - `uplift` 管"整片多高"，`hill_weight` 管"整片起伏多大"；
  - 地形类型 1/2/3 改 `amp`/`relief`（平原 2.4/0.7、丘陵 7.0/1.6、山地 11.0/2.0）；
  - 出生点 12 格内压平，向外每格最多抬/降 2 层（`SPAWN_FLAT`/`SPAWN_RAMP`）；
  - 上限 `_terrain_ceiling = 24`（[L252-L254](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L252-L254)）。
- `_kind_at()`：坡面/山顶露石、煤/铁矿石、4×4 沙地斑块、其余草（[L1239-L1267](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1239-L1267)）。
- 没有水、没有海平面、没有洞穴、没有 3D 密度、没有生物群系；"平原/丘陵/山地"是同一个噪声的三种振幅，不是群系。

**我们处在什么位置**：

- **"四倍频 64/19/6/2"** 在思路上就是 fBm（分形布朗运动）的 4 个 octave，但：
  - 用的是值噪声（不是梯度噪声）；
  - 四个 octave 的权重不是标准的 `persistence^n`，而是"大陆抬升 + 丘陵权重 + 细节 + 毛边"的手工塑形；
  - 频率比（lacunarity）≈ 64/19≈3.37、19/6≈3.17、6/2=3，属于常见范围（2~4）；
  - 额外加了 80 格分区噪声，相当于"手工生物群系"的雏形。
- 它**已经解决了**"两层太接近导致整片平"的问题（代码注释 [L1191-L1196](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1191-L1196)），能出成片低地/高地，这是 M1 阶段最关键的观感。
- 它**缺的是**：
  - 生物群系（温度/湿度/大陆性/侵蚀/怪异度的组合）；
  - 3D 密度（洞穴、悬空、地下）；
  - 海平面与水（`SEA_LEVEL` 目前没有）；
  - 高度区间（24 层 → M2a 的 64）；
  - 结构/地物（树之外）。

> 🔶 "要做得更像原版需要补什么"的优先级：
> 1. **先补海平面 + 水**（M2b E6）。没有水，地形再像也缺一半。
> 2. **再补"伪群系"参数**：把现在的 `zone` 噪声拆成 2~3 个低频参数（温度、湿度/侵蚀），用查表决定地表方块和树密度。不需要 5 参数 spline，也能出"森林/平原/山地"。
> 3. **最后补洞穴**（M2b E4）：用 3D 噪声阈值或"蠕虫隧道"都行，但必须和 M2a 的 section 架构一起做，否则会返工。
> 4. **不要追 1.18 的 spline/密度函数**：那是为了无限世界的宏观一致性，demo 的 512 格视距用不上，投入产出比很低。

### ③ 能落地的简化版本

1. **保留四倍频，但把参数表化**：`OCTAVES = [(64, w0), (19, w1), (6, w2), (2, w3)]`，`w` 可调；这样调参不用改公式。
2. **加"伪群系"**：
   - `temp = _noise01(x, z, 96, saltA)`、`wet = _noise01(x, z, 72, saltB)`；
   - 查表：`temp` 高 + `wet` 高 → 森林（树密度高、草顶）；`temp` 高 + `wet` 低 → 平原/沙地；`temp` 低 → 雪原（雪顶、树少）。
   - 这比"一个 zone 噪声"多一层，但仍然是 2D 的，成本可控。
3. **海平面**：M2a 定 `SEA_LEVEL = 32`（计划 Q20）；`height < SEA_LEVEL` 的列顶部填水方块（静态水，不做流动），`height == SEA_LEVEL` 附近生成沙/草。
4. **高度 64**：M2a 把 `_terrain_ceiling` 改成 `WORLD_HEIGHT`；地形振幅按比例放大，否则 64 层里只用 1~12 层会更平。
5. **洞穴**：M2b 用 3D 值噪声（`_noise3(x,y,z)`）做"阈值挖空"，只在近景/近区块算，远景跳过（LOD）。不要做流体。
6. **矿脉**：M2b 用"每区块固定数量的随机簇"（类似 `RandomPatchFeature`），按深度分层；不要做无限噪声矿脉。

## 5. 树木分布

### ① 原版怎么做（✅ 出处：[树木](https://minecraft.fandom.com/zh/wiki/%E6%A0%91%E6%9C%A8)、[森林](https://minecraft.fandom.com/zh/wiki/%E6%A3%AE%E6%9E%97)、[平原](https://minecraft.fandom.com/zh/wiki/%E5%B9%B3%E5%8E%9F)）

- **生成时机**：树木在**区块生成时**一并产生；也可以由树苗长成（✅ 树木页 §生长特性）。
- **分布算法**（✅ 树木页 + 群系页的组合，⚠️ 具体 JSON 数值未逐版本核对）：
  1. 每个生物群系有一组**地物（feature）列表**，每条 feature 有"每区块尝试次数 / 概率"；
  2. 每次尝试在区块内随机一个 XZ，按高度图找到地表；
  3. 做**合法性检查**：下方是泥土/草方块、上方有足够空间、光照足够（树苗生长要求亮度 ≥9；自然生成也类似）；
  4. 通过则按树种生成树干 + 树冠；树冠是直径约 5~7 格的球形/簇状，树叶必须邻接树干或相连树叶，否则消失（✅ 树木页 §结构）。
- **森林 vs 平原 vs 孤树**（✅ 群系页的树种比例）：
  - **森林**：普通橡树 72%、白桦 20%、珍异橡树 8%（✅ 森林页）；树密度高，所以成片。
  - **平原**：普通橡树 2/3、珍异橡树 1/3（✅ 平原页）；但平原的"每区块尝试次数"很低，所以是**稀疏孤树**，不是小森林。
  - **孤树**：本质是"低尝试次数 + 单点合法位置"的产物；不是单独一套算法。
- **怎么避免满图散点**：
  - 树只长在**有土壤**的地方（沙漠/海洋/岩石没有）；
  - 每个群系的**尝试次数**不同，森林高、平原低；
  - 群系本身是大块连续的（由气候参数决定），所以"树多/树少"也是成片的；
  - 合法性检查会淘汰悬崖、水边、空间不足的位置；
  - 树与树之间**没有强制最小间距**（原版森林里树可以挨得很近），"不散点"主要靠群系密度，而不是逐棵排斥。
  - ⚠️ 以上"尝试次数"的具体数值（如森林每区块 10 次、平原 0.1 次）是数据包 JSON 里的，Wiki 正文没有稳定列出；本轮未逐版本核对，不要写死。

### ② 我们当前实现与它的差距

- `_has_tree(cell)`（[L1270-L1292](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1270-L1292)）：
  - 出生点 6 格内不长树；
  - `forest = _noise01(x, z, 48, 41)`、`glade = _noise01(x, z, 23, 43)`；
  - `glade > 0.82` → 空地；
  - `weight = clamp((forest - 0.42) / 0.58, 0, 1)`；
  - `density = tree_percent * 100 / 9`；`hash % 10000 < density * weight * 5`。
  - 默认 `tree_percent = 10` → 林子中心约 5.55% 的列长树，边缘渐变到 0，空地完全没有。
- `_make_tree()`（[L799-L831](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L799-L831)）：
  - 固定 4 格树干 + 一份固定树冠网格；
  - 随机 90° 整数倍旋转（`_hash(cell, 31) % 4`）；
  - 整棵树是一个 `StaticBody3D`（4 格碰撞盒），挖掉任意位置都触发"整棵树消失 + 掉 1 木头"（[L885-L894](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L885-L894)）。
- 远景树：只画 4 根木头 + 一个树叶点（[L708-L714](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L708-L714)）。

**差距清单**：

| 项 | 原版 | 我们 |
|---|---|---|
| 分布依据 | 群系 feature 列表 + 每区块尝试 | 48/23 格低频噪声 + 逐格哈希 |
| 密度成片 | 群系大块连续 | 噪声成片（观感接近） |
| 最小间距 | 无强制，靠密度 | 无，可能两棵贴脸 |
| 树种 | 橡树/白桦/云杉等，按群系 | 只有一种"树" |
| 高度变化 | 4~7+ 格，树种相关 | 固定 4 格 |
| 树干/树叶 | 逐块，可单独挖 | 整棵一个碰撞体，挖一处全消失 |
| 合法性 | 土壤/空间/光照 | 只看出生点距离和噪声 |
| 孤树 | 低尝试次数的自然结果 | 靠 `weight` 边缘渐变 |

> 🔶 我们的做法在"避免满图散点"上其实比原版更直接：低频噪声直接决定"这一片是不是林子"。代价是树只长在草地、且没有树种/高度变化。对 M1/M2 的观感够用，但如果要"更像原版"，优先补的是**树种/高度变化**和**逐块树干**，而不是改密度算法。

### ③ 能落地的简化版本

1. **保留低频森林噪声**，但把 `_has_tree` 拆成两步：
   - `forest_density(x,z)`：低频噪声 → 0~1；
   - `can_place_tree(cell)`：检查地表是草/土、上方 5 格空气、离已有树 ≥2 格（用一个 `_tree_cells` 集合，生成时顺手记录）。
   这样能避免"两棵树重叠成一个方块团"。
2. **加 2~3 种树**：普通（4 格）、高树（5~6 格）、桦树（换皮/换叶色）。用 `_hash(cell, salt) % 100` 按群系权重选，不需要完整树种系统。
3. **树干逐块**：把 `_make_tree` 的树干从"一个 4 格碰撞体"改成 4 个独立方块（或一个 section 网格 + 逐块 meta），这样能还原"从下往上砍"的体验。代价是节点数 ×4，建议只在近景这样做，远景仍用合并网格。
4. **砍伐掉落**：树干逐块后，每块掉 1 木头；树叶掉树苗/苹果的概率可以不做（v1.0 没有树苗系统）。
5. **树苗生长**：M2b/E7 再做；现在不要提前加随机 tick，否则会打乱存档 diff。

### ④ 对应任务

- **M2b / E7（树苗 → 随机 tick 生长 → 树；生长与砍伐进存档）**：见 [L1172](file:///d:/BlenderGameKit/docs/plans/%E6%88%91%E7%9A%84%E4%B8%96%E7%95%8CDemo_%E6%80%BB%E4%BD%93%E8%AE%A1%E5%88%92_2026-11-10.md#L1172)。

## 6. 天气

### ① 原版怎么做（✅ 出处：[天气](https://minecraft.fandom.com/zh/wiki/%E5%A4%A9%E6%B0%94)、[Rain](https://minecraft.fandom.com/wiki/Rain)）

- **全局天气**：天气是**全局**的，同一维度所有位置同一天气；分晴天 / 降雨 / 雷暴（✅ 天气页 §机制）。
- **计时器**：降雨计时器 + 雷暴计时器；两者同时激活 → 雷暴。
  - 中文 Wiki：降雨通常持续 **3~13 分钟**，晴天 **10~150 分钟**（✅ 天气页 §机制）。
  - 英文 Rain 页：降雨平均 **0.5~1 个游戏日（10~20 分钟）**，两次降雨间隔 **0.5~7.5 个游戏日（10~150 分钟）**（✅ Rain 页 §Behavior）。
  - ⚠️ 两处降雨时长口径不一致（3~13 vs 10~20 分钟），可能是版本/版本页差异；引用时二选一并注明来源。
  - 概率：约 109/121 晴天、1/11 降雨、1/121 雷暴（✅ 天气页）。
- **降雨 vs 降雪**：由**生物群系温度**决定。温度 > 0.15 → 雨，≤ 0.15 → 雪；沙漠/热带草原/恶地等干旱群系无降水，只有阴天（✅ 天气页 §天气表现、Rain 页 §Behavior）。
- **高度影响**：温度随海拔下降，约每米 -0.0016，所以高山顶可能下雪、山脚下雨（✅ Rain 页 §Behavior）。
- **室内/地下**：雨粒子只落在"暴露在天空下的最高方块"上；实体方块会挡住雨（✅ Rain 页 §Rain particles 与 §List of blocks that can let rain go through；历史段也写"雨溅粒子出现在最高方块顶部"）。在 y=1 以下不生成雨粒子（✅ 同页）。下界/末地永远阴天，没有雨雪（✅ 天气页）。
- **雷暴**：额外降光照（天空光照 ≤10）、任何时候可睡觉结束、会生成闪电（✅ 天气页 §雷暴）。
- **光照**：降雨时内部天空光照不超过 12（✅ 天气页 §降雨）。

### ② 我们当前实现与它的差距

天气脚本在 [WEATHER_SCRIPT](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1471-L1596)：

- `NAMES = ["晴", "雨", "雪"]`，`DURATIONS = [70, 26, 20]` 秒，实际 ±15%（[L1476-L1478](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1476-L1478)）。
- `_physics_process` 计时到点就 `set_weather(index + 1)`，即 **晴 → 雨 → 雪 → 晴** 固定轮播（[L1494-L1502](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1494-L1502)）。
- 雨/雪只是换 `CPUParticles3D` 的 mesh/速度/颜色 + 调雾和背景亮度（[L1505-L1547](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1505-L1547)）。
- 粒子发射盒 9×9、位于天气节点上方 8 格（[L1566-L1595](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1566-L1595)）；**没有检查玩家头顶是否有屋顶/方块**，也没有"地下不显示"。
- 没有雷暴、没有闪电、没有生物群系温度、没有雨声、没有雨落地粒子。

**差距清单**：

| 项 | 原版 | 我们 |
|---|---|---|
| 天气种类 | 晴/雨/雷暴 | 晴/雨/雪（"雪"被当成一种独立天气） |
| 切换逻辑 | 两个随机计时器，按概率 | 固定顺序轮播 |
| 持续时长 | 分钟级（随机） | 20~70 秒 |
| 雨/雪判定 | 群系温度 + 海拔 | 直接当成两种天气 |
| 干旱群系 | 无降水 | 不存在群系，处处可下 |
| 屋顶/地下 | 雨被实体方块挡住 | 不判定，粒子照下 |
| 光照/雷暴 | 光照降低、闪电 | 只有雾/背景亮度 |
| 维度 | 下界/末地无雨 | 无维度概念 |

> 🔶 我们现在的"雪"其实是"把雨换成慢速白点"，不是原版的"寒冷群系降水"。如果目标是"像原版"，**不该把雪做成独立天气**，而应该让"雨"在寒冷区域自动变雪。但 v1.0 没有群系，所以现在的轮播是一个可接受的占位；等"伪群系"落地后再改。

### ③ 能落地的简化版本

1. **改成"天气状态 + 降水类型"两层**：
   - 状态：晴 / 雨（雷暴可以不做）；
   - 类型：在"雨"状态下，按玩家所在位置的伪群系温度决定显示雨还是雪。
   这样不用改很多代码，就能把"雪"从天气列表里拿掉。
2. **时长改随机**：`rain` 60~180 秒、`clear` 120~600 秒（demo 尺度，不是原版分钟级）；用两个计时器或一个状态机，避免固定轮播。
3. **屋顶判定**：从玩家/相机向上打一条 32 格射线（或查高度图），命中实体方块就 `emitting = false`；地下（`y < 地表 - 2`）也不发射。这个成本很低，观感提升明显。
4. **干旱区域**：用"伪群系湿度"为 0 的区域跳过降水；没有群系就先不做。
5. **雷暴**：不做闪电和火焰，最多把雾加浓、背景压暗；不要引入"雷暴刷怪"（M3 的 E9 再说）。
6. **雨声/落地粒子**：可以用一个 `AudioStreamPlayer3D` + 简单循环，落地粒子用少量 `GPUParticles3D`；不是必需。

### ④ 对应任务

- **M4 表现层**：云/雨雪粒子/画质档/帧数显示已经在 M4 范围（[L1086](file:///d:/BlenderGameKit/docs/plans/%E6%88%91%E7%9A%84%E4%B8%96%E7%95%8CDemo_%E6%80%BB%E4%BD%93%E8%AE%A1%E5%88%92_2026-11-10.md#L1086)）；天气没有单独任务 ID，建议挂 M4 / T5 的表现层收口。

  - 合成格里的材料会回到物品栏；物品栏满则掉在玩家附近（✅ 这是原版行为，⚠️ 具体"掉在脚下还是面前"版本相关）。
  - 光标上拿着物品时关闭界面：**旧版本是掉到世界，较新版本改为放回物品栏**（⚠️ 见 Mojira [MC-231366](https://bugs.mojang.com/browse/MC-231366)："it used to be that if you exited the inventory ... the item would drop. This is no longer the case - the item returns to the inventory." 该报告本身在讨论这是否是 bug，说明版本行为不稳定）。引用时不要把它写成"所有版本都 X"。
- **堆叠**：多数方块/物品 64；工具/盔甲 1；部分物品 16（✅ 物品栏页/物品页；具体物品见各自页面）。

### ② 我们当前实现与它的差距

**差距清单**：

| 项 | 原版 | 我们 |
|---|---|---|

> 🔶 我们的 UI 是"能用"的 M1 闭环，但和原版的**操作手感**差距主要在：
> 1. 没有右键拆半/放 1 个；
> 2. 没有 Shift 快捷移动；
> 3. 配方无序，摆错位置也能合成（原版有序配方会失败）。
> 这三项里，**Shift 快捷移动**对玩家效率影响最大，**右键**次之，**有序配方**最不重要（demo 配方少，无序更友好）。

### ③ 能落地的简化版本

1. **右键支持**（改 `_click_container`）：
   - 空手 + 右键空槽：不做（原版是放 1 个，但手里没东西）；
   - 手里有堆 + 右键空槽：放下 1 个；
   - 手里有堆 + 右键同类槽：放 1 个；
   - 空手 + 右键有物品槽：拿起一半（`ceil(count/2)`）。
2. **Shift 快捷移动**：给 `_click_container` 加一个 `shift: bool` 参数：
   - 背包/快捷栏 → 已打开的箱子/合成格；
   - 箱子/合成格 → 背包；
   - 目标容器按"先合并同类、再找空槽"的顺序放，放不下的留在原槽。
   这正是原版的行为，代码量不大（复用 `add_item` 的思路）。
3. **拖动分配**：如果做，建议先做"左键拖动平均分配"，右键每格 1 个可以后补；但要注意和现有"按下/松手"逻辑冲突，最好改成"按住移动时逐格处理"。
4. **有序配方**：给配方加一个可选的 `pattern`（3×3 字符串数组），有 pattern 就按形状匹配，没有就按无序。现有 4 条配方可以保持无序，避免玩家摆错就合不出来。
5. **关闭规则**：保持"回包，塞不下掉脚边"；这比"直接消失"安全，也接近较新版本。合成格材料同理。
6. **大箱子**：不做。它需要相邻方块检测、朝向、54 格 UI 和存档合并，收益低。

## 8. 玩家皮肤

### ① 原版怎么做（✅ 出处：[皮肤](https://minecraft.fandom.com/zh/wiki/%E7%9A%AE%E8%82%A4)；UV 坐标见下方说明）

- **文件**：Java 版皮肤是 **64×64 PNG**（旧版 64×32 会在导入时转换）（✅ 皮肤页 §属性；[PixelForge 模板](https://mcpixelforge.com/skin-template) 的说明与此一致）。
- **两层**：
  - 第一层（base）：实体本体，**不允许透明**；
  - 第二层（overlay / hat / jacket / sleeve / pants）：**允许透明**，默认透明，用来做帽子、夹克、袖子、裤腿（✅ 皮肤页 §属性）。
  - 第二层比第一层**略微外扩**，所以能看到"衣服浮在皮肤上"的厚度；常见资料说头部约 0.5 像素、身体/四肢约 0.25 像素（⚠️ 这是社区文档的常见值，官方 Wiki 本轮没给出逐部位数值；建议按"头部 0.5、其余 0.25"实现，并在视觉上微调）。
- **UV 分区**（✅ 与 [PixelForge 模板表](https://mcpixelforge.com/skin-template) 一致；这是社区整理，原版 Wiki 的 UV 图本轮没抓到，标 ⚠️）：

| 部位 | 尺寸（宽×高×深） | 第一层 x,y | 第二层 | 第二层 x,y |
|---|---|---|---|---|
| 头 | 8×8×8 | 0–32, 0–16 | 帽子 | 32–64, 0–16 |
| 身体 | 8×12×4 | 16–40, 16–32 | 夹克 | 16–40, 32–48 |
| 右臂 | 4×12×4 | 40–56, 16–32 | 右袖 | 40–56, 32–48 |
| 左臂 | 4×12×4 | 32–48, 48–64 | 左袖 | 48–64, 48–64 |
| 右腿 | 4×12×4 | 0–16, 16–32 | 右裤腿 | 0–16, 32–48 |
| 左腿 | 4×12×4 | 16–32, 48–64 | 左裤腿 | 0–16, 48–64 |

- **面展开**：每个部件是一个盒子，六个面按"上/下在上排，四个侧面按右/前/左/后展开"排列；头部正面在 x 8–16, y 8–16（✅ 模板页说明）。
- **手臂粗细**：经典 Steve 手臂 4 像素宽；Alex 纤细手臂 3 像素宽，其余不变（✅ 皮肤页 §Java版；模板页）。
- **优先级**：用户上传的皮肤 > 资源包默认皮肤 > 内置默认（计划 Q19 已拍板，见 [L1053](file:///d:/BlenderGameKit/docs/plans/%E6%88%91%E7%9A%84%E4%B8%96%E7%95%8CDemo_%E6%80%BB%E4%BD%93%E8%AE%A1%E5%88%92_2026-11-10.md#L1053)）。

### ② 我们当前实现与它的差距

- 生成器按 64×64 排 UV：`SKIN_HEAD/BODY/ARM/LEG` 六个面的矩形（[L5946-L5966](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L5946-L5966)）。
- 模型拆成头/身/两臂/两腿，外层壳 `grown = 0.06`（米），**只给头、身、臂加壳，腿跳过**（[L6063-L6096](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L6063-L6096)，注释"裤子不做外套壳，不然腿会粗一圈"）。
- 外层材质用 `surface 1`，透明 + `depth_draw_mode = DEPTH_DRAW_DISABLED`（[L1838-L1850](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1838-L1850)）。
- **外层贴图写入的是第一层 UV 矩形**：`_player_skin_outer_rows()` 用 `SKIN_HEAD[1]`（本体头顶）、`SKIN_BODY[2:]`、`SKIN_ARM[2:]`（[L6025-L6039](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L6025-L6039)）；`make_skinned_player_mesh()` 给两层都用 `SKIN_PART_RECTS[part]`（[L6095](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L6095)）。也就是说：**原版 64×64 皮肤的第二层区域（x 32–64）完全不会被采样**。
- 模型比例：头 0.45m、身 0.55m 高、腿 0.65m，总高 1.65m（[L5955-L5963](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L5955-L5963)）；原版玩家 1.8m（头 0.5、身 0.75、腿 0.75，⚠️ 按像素换算的近似）。
- 皮肤加载：优先 `user://skin/mc_skin.png`，否则 `res://art/skin/mc_skin.png`；外层同理（[L1827-L1842](file:///d:/BlenderGameKit/scripts/make_minecraft_demo.py#L1827-L1842)）。这个优先级符合 Q19 的"用户皮肤 > 资源包 > 内置"。

**差距清单**：

| 项 | 原版 | 我们 |
|---|---|---|
| 64×64 | 是 | 是 |
| 第一层 UV | 标准 | 基本对齐（头/身/臂/腿） |
| 第二层 UV | 独立区域（32–64, 0–64） | **复用第一层 UV**，原版第二层贴图不生效 |
| 第二层覆盖 | 头/身/双臂/双腿 | 头/身/双臂，**没有腿** |
| 外扩 | 头约 0.5px、其余约 0.25px | 统一 0.06m |
| 手臂粗细 | 4px（Steve）/ 3px（Alex） | 固定 0.16m，无 slim |
| 模型比例 | 1.8m | 1.65m |
| 皮肤优先级 | 用户 > 资源包 > 内置 | 已是这个顺序 |

> 🔶 这是"看起来能换皮肤，但换原版皮肤时外套层不显示"的典型问题。第一层没问题；第二层需要**独立的 UV 表**，而不是复用第一层。这个改动主要集中在 `SKIN_*` 常量和 `make_skinned_player_mesh()` 的 `face_uvs`，不影响游戏逻辑，适合在 M4 做。

### ③ 能落地的简化版本

1. **给第二层加独立 UV 表**：
   - `SKIN_HEAD_OUTER = ((40,0,8,8),(32,0,8,8),(48,8,8,8),(32,8,8,8),(40,8,8,8),(48,8,8,8))`（示例，按"帽层"的展开顺序）；
   - 身体/臂/腿同理，按模板表的第二层 x,y 推。
   - `make_skinned_player_mesh()` 里 group 1 用 `SKIN_PART_RECTS_OUTER[part]`。
2. **补腿的外套**：去掉 `if group == 1 and part == "leg": continue`，给腿也加壳。注意外扩别太大，否则腿会明显变粗。
3. **外扩按部位**：头 `0.5/16 = 0.03125m`，身体/四肢 `0.25/16 = 0.015625m`（按 1px=1/16m 换算）。现在的 0.06m 偏大，可以调小。
4. **slim 手臂**：如果做，给 `PLAYER_PARTS` 加一个 `arm_width` 参数，并在 UV 上把手臂的 4px 改成 3px；不做也不影响第一层。
5. **模型比例**：如果只是第一人称/第三人称看，1.65m 够用；要做"和原版一样高"再改 1.8m，但会牵动相机高度、碰撞盒、HUD，不建议顺手改。
6. **默认皮肤**：保留现在的程序化 Steve 配色，但把外层默认写成全透明；这样用户放原版皮肤时，第二层直接生效。

## 9. 建议的落地顺序（只列与本文相关的）

> 原则：不打断现有 **T4c → M1-R → M2a → M2b** 的顺序（计划 [L1477-L1486](file:///d:/BlenderGameKit/docs/plans/%E6%88%91%E7%9A%84%E4%B8%96%E7%95%8CDemo_%E6%80%BB%E4%BD%93%E8%AE%A1%E5%88%92_2026-11-10.md#L1477-L1486)）。

1. **M1-R 内可顺手做**（不动架构、收益高）：
   - 放置占用检查把玩家/实体算进去（E3，几行）；
   - 右键拆半 + Shift 快捷移动（S-INV/E2，UI 手感）；
   - 挖掘换手持物品归零 + 0.25s 冷却（E1/E12，小改）；
   - 把手里的方块放进自己身体的问题修掉（同上）。
2. **M2a**：
   - section 化 + 高度 64/海平面 32 + 分级碰撞；
   - 把 `HARDNESS` 改成"硬度 + 工具倍率 + 品质表"（与高度改动同批，避免两次回归）。
3. **M2b**：
   - 洞穴/矿脉/静态水；
   - 树木逐块树干 + 2~3 种高度；
   - 伪群系（温度/湿度）驱动地表方块与树密度。
4. **M4**：
   - 皮肤第二层独立 UV + 腿外套 + 更小的外扩；
   - 天气改成"晴/雨 + 温度决定雨雪"，加屋顶判定。
5. **M5**：
   - 皮肤优先级接入资源包（用户 > 包 > 内置）。

**不建议做**（投入产出比低 / 会破坏现有验收）：

- 完整 1.18 的 5 参数 spline + 3D 密度函数；
- 流体模拟、红石、村庄、附魔、酿造；
- 大箱子、盔甲槽、副手槽；
- 后台线程区块构建、区块 LOD、光照传播；
- 工具耐久/附魔/时运/精准采集。
