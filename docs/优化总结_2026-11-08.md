> 本轮目标：节点系统逻辑、功能扩展性、画面渲染、向 UE5 蓝图靠拢、清理过期内容。
> 约束：保持"一小部分渲染与运行在 Godot，剩下的设计/建模/逻辑都在 Blender"。

> 补 UE5 能力 + 加扩展点 + 加自检层"，并给渲染补上像素级证据。

## 二、节点系统逻辑修复

### 2.1 『只执行一次』的重置引脚

- 文件：`BlenderGameKit/codegen/statements.py`（`_stmt_do_once`）
- 现在只在**引脚真的接线**时生成 `if <上游>: done = false`。
- 未接线时**产物逐字不变** —— 老图就算把布尔默认值改成 True，也不会突然
  从"只跑一次"变成"每次都跑"。
- 回归：`test_do_once_reset_pin_is_really_used`。

### 2.2 FlipFlop / MultiGate 的状态推进时序

代码审查抓到的真问题：原来"先走分支、末尾再改状态"。
分支里只要有 `await`（『等待_秒』『等待_可重触发』），第二次触发会在
await 结束前读到**旧状态** —— 表现是连续两次都走同一支 / 同一个出口。

- 修法：**先取号并推进状态，再进 `if` / `match`**。
- 文件：`codegen/statements.py`（`_stmt_flip_flop`、`_stmt_multi_gate`）。
- 回归：测试里断言 `_gk_ff = not _gk_ff` 出现在 `if` 之前、
  `_gk_mg += 1` 出现在 `match` 之前。

### 2.3 多入口节点不再被误判成执行流回路

- 文件：`BlenderGameKit/codegen/registry.py`
- 断环键从 `node` 改为 `(node, entry)`。
- 『流程_门』的『打开 / 关闭 / 切换』、『流程_多路门』的『重置』是合法入口；
  同一条链里再次进入**另一个入口**不再报"游戏里会无限循环"。
- 回归：`test_gate_other_entry_is_not_a_cycle`。

### 2.4 两个扩展点（给以后加节点用）

| 扩展点 | 位置 | 作用 |
|---|---|---|
| `ctx.current_entry` | `codegen/context.py` + `codegen/registry.py` | 处理器能知道"这次从哪个执行入口进来"，多入口节点不用再挤在同一个入口里猜 |
| `gk_owns_flow = True` | `codegen/context.py`（`emit_statement`） | 节点自己负责下游执行流时，生成器不再自动续接一次（否则带 `await` 的分支会把下游生成两遍） |

## 三、向 UE5 蓝图靠拢：新增 8 个节点

| 节点 | 对应 UE5 | 说明 |
|---|---|---|
| **流程_门** | `Gate` | 『执行』按门状态走『开』/『关』；『打开』『关闭』『切换』只改状态 |
| **流程_翻转** | `FlipFlop` | 每次执行 A / B 交替；可勾『先走 B』 |
| **流程_多路门** | `MultiGate` | 每次执行走下一个出口；出口 1~8 可调；『循环』/『重置』 |
| **流程_当条件** | `WhileLoop` | 条件为真就一直跑循环体；条件常量 `true` 会告警 |
| **流程_多路文本** | `Switch on String` | 按 `红\|绿\|蓝` 分支走不同出口，不匹配走『默认』 |
| **等待_可重触发** | `Retriggerable Delay` | 等待期间再触发会重新计时，只有最后一次通过（代号/Generation 实现） |
| **列表_遍历** | `ForEachLoop` | 逐项跑『循环体』，`当前项` / `下标` 可接进循环体；空列表也走『结束后』 |
| **运算_选择** | `Select` | 条件为真取 A、为假取 B |

### 选择节点的类型稳定性（代码审查抓到的阻塞问题）

第一版直接生成 `(A if 条件 else B)`。A/B 未接线时在真实 Blender 里拿不到
`default_value` → 生成 `null`；两边类型不同时结果是 `Variant`。
下游只要写 `var x := ...`（动画播放、移动方向都是这么写的），Godot 4.7
就报 `inference_on_variant`，**整份脚本加载失败**。

现在『运算_选择』先选**类型**（数值 / 文本 / 布尔 / 向量），生成时调用
一个 Variant 参数的转换辅助函数（`_gk_select_float` / `_text` / `_bool` /
`_vec`），在函数里按 `is` 判断后转换。空引脚给对应类型的零值，
**接错类型**（例如向量接到数值选择）也不会生成 `float(Vector3)` 这种
Parse Error。辅助函数每种类型只生成一份，返回类型是具体的
`float` / `String` / `bool` / `Vector3`，下游 `var x := ...` 能正常推断。
回归覆盖了数值、文本、空引脚、错配四种。

### 遍历节点的重入（已修）

第一版把 `当前项` / `下标` 放在脚本成员变量里：同一个遍历节点如果在循环体里
被再次触发，后一次会覆盖前一次，前一次 `await` 醒来后读到别人那一项。

现在循环体里读的是**本次遍历的局部变量**（协程各自一份，互不干扰），
每轮同时把值抄进成员变量，供"循环结束后还想读最后一项"的卡片使用；
在循环体外读会走成员镜像并给一条提示，不会出现作用域错误。

## 四、画面渲染优化（本轮重点）

### 4.1 三色调真的变成三档

- 文件：`BlenderGameKit/shaders/gk_toon.gdshader`
- 旧逻辑：先算 `gk_ramp()` 三段色，再用 `lit_factor` 在
  `shadow_col` / `lit_col` 之间二选一。`lit_factor` 在整个阴影区都是 0，
  所以中间那档**永远选不中** —— `three_tone` 和两色调出图完全一样。
- 新逻辑：每一档用自己的阈值和颜色：
  - `raw < min(shadow_step_2, shadow_step - 0.001)` → `shadow_tint_2`
  - 中间 → `shadow_tint`
  - `raw > shadow_step` → `lit_tint × 光照`
- 防黑地板也跟着模式走：两色调用 `shadow_tint`，三色调用
  `shadow_tint_2`，避免"深阴影色比普通阴影还亮"时污染两色调。

### 4.2 Blender 预览与运行时对齐

- 文件：`BlenderGameKit/npr_preview.py`（`_configure_ramp`）
- 两色调的底部色标改用 `shadow_tint`（和运行时一致）。
- 三色调的中间色标落在第二道分界 `shadow_step_2` 上，才是真正的三段。
- 删掉了预览参数表里两个运行时早就不存在的项：`shadow_strength`、
  `light_map_mix`。

### 4.3 像素级验证（不是"看着差不多"）

新增 `examples/demo_render/tone.tscn` + `tone_probe.gd`：
一颗球、纯色背景、光正对相机；沿画面中线数"出现得够多的量化颜色"。

| 材质 | 期望 | 实测 |
|---|---|---|
| 两色调 | 2 档 | **2 档** |
| 三色调 | 3 档 | **3 档**（深紫 / 浅紫 / 白） |

`scripts/check_render_demo.py` 现在会断言：
`bands_two == 2`、`bands_three >= 3`、`three > two`。
三色调如果退化成两档，这一层直接判红。

> 调试时踩到的坑：透视投影下"可见表面"的法线分量最多只到 `R/d ≈ 0.28`，
> 第二道分界放在 -0.15 附近时深阴影环只有几个像素宽，会被抗锯齿抹掉。
> demo 材质已把阈值放到 0.70 / 0.90，让三档都有足够可见面积。

### 4.4 面部阴影 SDF 回归（本轮发现的隐藏缺口）

切到 `unshaded` 的那次重构把**运行时**的面部 SDF 整段漏掉了：文档、demo、
Blender 预览都还在设 `face_sdf_mix`，但 `gk_toon.gdshader` 里根本没有这个
uniform —— 参数看着有、画面永远不变。

本轮把它接回来了，并修掉两个真问题：

1. `VIEW` 方向符号写反：`clamp(-dot(view_dir, light_view))` 会让**整张脸
   永远全阴影**。Godot 的 `VIEW` 是从相机指向片元，背后光才是正点积。
2. 采样方式错误：旧代码用"线位置"替掉 `UV.x`，整个面片只采同一列，
   自然是一条常数。正确做法是 **`UV.x + (line - neutral)`**（和
   `npr_preview.py` 里 Blender 预览那套节点一致）。

同时补上了 Blender 端到端：

- 材质自定义属性新增 `面部阴影贴图` / `面部用 UV2` / `面部上下微调`；
- `write_npr_material` 会把 `face_sdf` 贴图落盘成 `art/ui_xxx.png` 并写进
  `.tres`，且**不写** `use_face_sdf`（着色器用 `face_sdf_mix` 当开关）；
- `face_sdf_angle` 是 Blender 预览专用系数，导出时跳过，避免 Godot 刷
  "shader parameter not found"；
- demo 面部材质补了 `use_albedo_texture = 1.0`，脸片不再是一块纯色。

验证：扫光截图在 0° / 90° / 270° / 180° 都能看到分界线移动 / 整脸压暗；
`gk_toon` 与 `gk_toon_lit` 两条路径都接上了。

### 4.5 主光 + 补光（多光源）

以前每帧只挑**影响最大的一盏**灯喂给卡通材质，第二盏及以后完全不参与 ——
侧光 / 补光在 Blender 里调好了，进 Godot 却没有效果。

本轮：

- 环境脚本改为 `_gk_pick_lights(..., 2)` 按影响取**前两盏**：
  第一盏写 `light_dir` / `light_color` / `light_energy`，
  第二盏写 `light_dir_2` / `light_color_2` / `light_energy_2`；
- 着色器新增 `light_step_2`（补光自己的明暗分界，默认 0 = 整个朝向
  补光的半球都受光）；补光叠加在当前档位的阴影底色上，再与主光色阶取
  `max` —— **只加亮不压暗**，主光色阶不会被洗灰；
- 补光同样接面部 SDF（`face_sdf_mix` 对第二盏灯生效）。

调试时踩到的坑：补光一开始借用主光的 `shadow_step`（0.85）当阈值，结果
只点亮球最边缘几个像素的一圈 —— 静态 grep、着色器编译、单张截图全部
“通过”，只有 `fill.tscn` 的**同一区域亮度对比**抓到了。现在阈值独立成
`light_step_2`，demo 探针断言 `on > off + 0.05`（实测 0.355 → 0.741）。

补光还做过一次可用性修正：如果只做 `max(主光结果, base × 补光能量)`，
真实场景里 0.15~0.25 的补光会被 0.4 左右的卡通阴影底**吞掉**（画面上
完全没变化）。所以补光现在**叠加在当前档位的阴影底色上**，弱补光也能
把阴影抬起来（0.25 能量把阴影从 0.4 抬到 ~0.65），而亮部由外层 `max`
保持原色阶。

> 超过两盏灯时仍只取影响最大的两盏 —— 每增加一盏都要多一组 uniform 和
> 一段 band 计算，而且第三盏对卡通分档的贡献通常会被前两盏盖住。

### 4.6 文档与 demo 清理

- `docs/渲染-NPR卡通着色.md`：
  - 修正"`light()` 里没有 `SPECULAR_LIGHT`"的过期结论（4.7.2 实测存在，
    `gk_toon_lit.gdshader` 正在用）；
  - 删除 `backlight_amount` / `light_map` 的参数说明，标明它们已从着色器移除；
  - 参数数量改为 24。

### 4.7 相机远裁（第一百九十轮）

Godot 的 `Camera3D.far` 默认 4000 米；调小会让远处物体凭空消失，是视觉
bug 不是优化，所以一直没做。现在做成了**每台相机一个属性 + 面板警告**：

- 相机物体 →『游戏物理』→ **远裁距离**（0 = 不导出，用默认 4000 米）；
- 相机也常在 glb 实例内部，属性写进环境脚本的 `camera_fars` 表，运行时
  由 `_apply_camera_far` 按名字设置；
- 填得比 `near` 还小时按 `near + 0.01` 兜底，避免整台相机画不出东西；
- 面板上直接写明“调小会让远处物体凭空消失”。

真机验证（无头即可）：`scripts/check_camera_far.py` 起三台相机，确认
150 → 150、0.01 → 0.06（near 兜底）、没填的保持 4000。

### 4.8 节点图 → C++ 热路径（第一百九十一轮）

默认导出仍是 GDScript；这一轮加的是**可选**的 C++ 热路径生成器：

- 侧栏导出按钮旁新增『C++ 热路径』；
- 只提取 `物理帧 → 输入_方向 → 移动_按方向 [→ 水平翻转] →
  分支(在地面 且 跳跃键) → 移动_跳跃`；
- 生成 `native/` 下的 GDExtension 源码 + SConstruct / CMake / build.ps1 /
  .gdextension / README；
- 生成的是**伴随节点**（`GKHotPath2D` / `GKHotPath3D`，extends Node）：
  C++ 只接管移动，其它事件仍由 GDScript 负责；
- 移动链里出现寻路 / 推开刚体 / 上台阶 / 相机相对方向等节点时
  **直接拒绝并点名**，不生成半成品；
- 正常导出产物不变（不点这个按钮就不会多任何文件）。

真机验证：`scripts/check_cpp_hot_path.py` 生成源码、用 SCons + 本仓库
godot-cpp 真编译，再让 Godot 加载并检查 `GKHotPath2D` 存在 +
`speed` / `action_jump` 可读写。

### 4.9 GDScript → 节点图（第一百九十二轮）

反向能力：侧栏 **『从 GDScript 导入』** 选一个 `.gd`，新建一张
『游戏逻辑』图。

- 支持 `extends` / `const ACTION_*` / `@export var` /
  `_ready` / `_process` / `_physics_process`；
- 物理帧的标准移动链整条还原：输入 / 移动 / 翻转 / 在地面且跳跃键 / 跳跃；
- 普通语句支持 `print` / `await` 等待 / `queue_free` / 数值赋值 / `if` 分支；
- 条件支持按键、在地面、与 / 或 / 非、数值或变量比较；
- 不认识的语句**带行号告警并跳过**，插件自动生成的 `_gk_*` 辅助函数跳过；
- 明确**不是**通用 GDScript 解析器（复杂语法不支持，避免"导入成功但行为不对"）。

验证：离线 1446；Blender 冒烟 672 / 面板 126；真 Blender 往返
（真树生成代码 → 导入新树 → 再生成代码）移动链 / 速度 260 / 跳跃力 560
全部回来。

### 4.11 验证脚本存档隔离 + 七色闯关进门禁（第一百九十四轮）

`scripts/check_shichise.py` 一直没敢进常规回归，原因写在文件头：它的探针要
删 `user://gk_shichise.json` 保证"从零开始"，删的是开发用的**真实存档**。

- 跑 Godot 时把 `APPDATA` / `LOCALAPPDATA`（Windows 上 Godot 用它们定位
  `user://`）指到 `_dist/shichise_probe_profile`，Linux/macOS 的
  `XDG_DATA_HOME` / `HOME` 一并指过去 —— 删的只是那份临时存档；
- 新增一条断言"隔离目录真的被建出来了"。这条防的是**隔离悄悄失效**：
  万一以后 Godot 换了定位变量，探针又会删真实存档，而所有行为断言照样全绿；
- 接进 `build_and_test.ps1`（5s-5）：没有 `games/七色/七色_godot` 时跳过
  （那个目录在 `.gitignore` 里，是本地生成物），有工程才真跑。

顺手发现本地的 `七色_godot` 是第 187 轮留下的旧导出：关卡树里一个
『脚本_加载』指向了导出报告文本（`GK_c04dafde.gd` 里是一份导出报告），
世界脚本没被加载。用 `make_shichise.py` 重建后恢复：世界 / 敌人 / 玩家
三个自定义脚本都挂在正确的宿主上。

真机检查：`python scripts/check_shichise.py` → **CHECK_SHICHISE=OK**
（34 项：对话拿火把 / 三座火盆 / 塔门升到 12.4 / 敌人 60→40 /
BOSS 现身 / 击杀后 `red_restored=true`、饱和度 1.5）。

### 4.12 我的世界：四档方块 + 数字键切换（第一百九十五轮）

`demo_minecraft` 原来只能放同一种方块。这一轮把"手上拿哪一档"补上：

- `blocks/` 里四种可放置方块（草 / 石 / 沙 / 木），每种一份 `PackedScene`，
  颜色各不相同；
- 侧栏变量 `方块序号`（float，0~3）+『变量_读取』+『多路分支』
  （Switch on Int，出口 0~3）—— 蓝图里"按枚举选资产"那种写法；
- 数字键 1~4（`slot_1`~`slot_4`）→『如果_否则』→『变量_设置』；
- 『序列』扩到 8 步：转视角 / 挖 / 放 / 选 1~4 / ESC。

真机检查（`check_minecraft_demo.py`）除了原来的落地 / 移动 / 跳跃 / 挖，
还会：默认放草方块并核对颜色 → 按 2 放石头方块 → 按 4 放木头方块，
四种方块按名字 + `albedo_color` 双重确认（`grass=1 stone=1 wood=1`）。

### 4.13 我的世界：会追人的小怪 + 生命 HUD（第一百九十六轮）

"能放、能走、怪物会打你"三件事补齐：

- `Main.tscn` 里加 `Monsters` 分组，三只 `CharacterBody3D` 红皮怪
  （碰撞层 `mobs`，和方块 / 玩家分开）；
- 追击用『移动_朝向目标』：脚本在玩家身上，"谁走"写相对路径
  `../Monsters/怪物N`、目标填自己，怪物每物理帧朝玩家走（`look_at` 转向）；
- 攻击 = 三只怪物的『到达』求或 →『流程_冷却(1 秒)』→『变量_增减(生命, -8)』；
  掉到 0 时『变量_设置(生命=100)』+『移动_设置位置(出生点)』+ 打印提示；
- HUD 每物理帧刷『界面_文本(生命 N)』+『界面_进度条』，扣血时
  『界面_飘字』冒一行 "生命 -8"；
- 跳跃 / 扣血用『序列』分成两条独立出口，避免共用的下游被生成器复制两遍。

真机检查新增：三只怪物都要追到 2 米内（实测 0.75）、生命从 100 往下掉
（实测 76→44）、HUD 文字确实存在且以 "生命 " 开头。

## 五、功能扩展性

### 5.1 节点声明自检层

新增 `BlenderGameKit/nodes/node_schema.py`（纯标准库，不依赖 bpy）：

- `gk_input_props` 指向的引脚 / 属性必须存在；
- 引脚名不能为空、同一侧不能重名；
- 分类必须在 `CATEGORY_ORDER` 里；
- 标签唯一、`gk_doc` 非空。

`tests/test_node_schema.py` 对**全部 267 个节点**跑一遍，并验证"坏映射 /
重名标签"真的会被报出来。以后加节点不必靠人肉记忆检查这些约定。

### 5.2 新增节点的标准步骤（写在这里，避免每次都翻代码）

1. 在 `nodes/_<领域>.py` 里用 `@N` 声明类：`bl_idname` / `bl_label` /
   `gk_category` / `gk_doc` / `gk_inputs` / `gk_outputs`；
2. 需要动态引脚就重写 `build_sockets()`，属性名带 `count` 会自动重建；
3. 在 `codegen/statements.py` 或 `codegen/expressions.py` 写处理器；
   节点自己管下游就声明 `gk_owns_flow = True`；
4. 多入口节点读 `ctx.current_entry` 区分入口；
5. 加离线测试，再跑 `python scripts/make_node_docs.py`。

### 5.3 为什么不做全量重写

- 现有 codegen 已经覆盖 267 个节点、多层门禁（离线 / 真 Blender / 真 Godot /
  真 GPU 渲染 / 真游玩）；
- 全量换节点系统会同时改 Blender RNA、序列化、菜单、文档、示例和所有测试，
  风险不可控；
- 本轮改为"在关键位置留扩展点 + 加自检层 + 补能力"，收益/风险比更高。

## 六、清理

### 6.1 根目录

删除（都是误生成 / 备份残留）：

- `-b/` —— 一次命令行把 `-b` 当路径生成的 Godot 工程；
- `%SystemDrive%/` —— 环境变量没展开导致复制进来的 Windows 缓存目录；
- `临时.blend1` —— Blender 自动备份，没有对应的 `临时.blend`。

### 6.2 示例

逐个核对后**没有删除示例**：

- `demo_anim_tree` / `demo_2d_blend` 虽然标着"旧示例"，
  但 `verify_anim_system.ps1` 的 `-Deep` 层仍会重建并校验它们；
  删了会让那两层失去覆盖。
- `demo_ui` 与 `demo_ui_v2` 是"基础界面"与"新控件/新功能"两套，
  门禁分别有探针，不是重复目录。
- `check_examples.py` 对每个目录都有"有效 / 白名单 / 门禁"判定，
  本轮复跑 `CHECK_EXAMPLES=OK`。

清理的是**产物层面**的过期内容：demo 材质里的废弃 uniform、
文档里的失效参数，而不是删掉仍被门禁使用的示例。
